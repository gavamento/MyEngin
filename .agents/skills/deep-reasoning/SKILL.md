# Deep Reasoning Protocol

このスキルは「賢く見える出力」ではなく「正しい結論に到達するプロセス」を規定する。
中心原理は3つ：**不確実性から着手する / 証拠が仮説に勝つ / 次に決めることを意図的に選ぶ**。

## 1. タスクの分解 — 構造ではなく不確実性で切る

やってはいけない分解：成果物の見た目どおりに切る（「まずファイルAを作り、次にBを…」）。
これは最大のリスクを最後まで温存し、終盤で計画全体が崩れる。

正しい分解の手順：

1. **未知を列挙する。** このタスクで自分がまだ知らないこと・確信がないことを書き出す。
   「知っているつもり」も疑う — 記憶で答えず、コードや資料で確認できるものは未知に分類する。
2. **荷重のかかる決定（load-bearing decision）を特定する。**
   間違っていたら下流の作業がすべて無駄になる判断はどれか。それを最初に検証する。
3. **最も安く潰せる致命的リスクから着手する。**
   「計画を無効化しうる安価な確認」＞「計画に沿った高価な作業」。
   例：APIが想定どおり動くか10行のスクリプトで確かめてから、本実装に入る。
4. **薄い縦切り（vertical slice）を先に通す。** レイヤーごとに完成させるのではなく、
   最小の入力→出力が端から端まで通る経路をまず1本作る。統合の問題は早く露見させるほど安い。
5. **各サブタスクに検証手段を紐づける。** 「終わったかどうかを機械的に判定できない
   サブタスク」は分解が甘い証拠。完了条件を観測可能な事実で書く。
6. **可逆と不可逆を区別する。** 元に戻せる操作（two-way door）は考えすぎず実行して学ぶ。
   元に戻せない操作（one-way door：削除、公開、外部送信、破壊的マイグレーション）だけ熟慮する。

## 2. 自己検証 — 自分の結論を反証しにいく

「動いたはず」「コンパイルが通った」「見た目正しい」は検証ではない。

- **予測してから実行する。** コマンドやテストを走らせる前に、期待する出力を具体的に言語化する。
  結果が予測と違ったら、それは自分のシステム理解が間違っているシグナル。
  作業を進める前に、まずメンタルモデルを修正する。予想外の成功も予想外の失敗と同じく調査対象。
- **敵対的に自己レビューする。** 結論を出したら、立場を反転して「これを壊す入力は何か」を探す。
  空・1件・大量・境界値・同時実行・不正入力・Unicode・タイムゾーン。
  自分の修正が正しい理由を探すのではなく、間違っている可能性を探す。
- **故障点で検証する。** バグ修正は、元の失敗を再現していた条件そのもので確認する。
  ハッピーパスが通ることは、バグが直ったことの証明にならない。
- **証拠は仮説に勝つ。** 観測結果が仮説と矛盾したら、観測を疑って仮説を守る（合理化）のではなく、
  仮説を捨てる。同じ箇所をもう一度、先入観なしで読み直す。
- **主張は一次情報で裏を取る。** 「このライブラリはこう動くはず」と書く前に、実際のコード・
  ドキュメント・実行結果を見る。記憶からの断定は、確認済みの事実と区別して明示する
  （「確認した」「推測だが」「未検証」を言い分ける）。
- **エンドツーエンドで動かす。** テストが通ることと、実際のフローで機能することは別。
  可能なら本物の経路（アプリを起動する、実データを流す）で観測してから完了を宣言する。

## 3. 次に決めることを決める — メタ意思決定

行き詰まりの多くは「答えられない問いに答えようとしている」ことが原因。
各ステップで、作業に入る前にこう問う：

- **「答えが出れば次の行動が最も変わる未解決の問いはどれか？」** それに先に答える。
  行動が変わらない問いは、いくら面白くても今は調べない。
- **情報の価値÷取得コストで並べる。** 5分で計画を無効化できる確認は、
  2時間の実装より先。逆に、どちらに転んでも同じコードを書くなら、調査を打ち切って書く。
- **自分で調べられる事実と、ユーザーにしか決められない選択を区別する。**
  コードを読めばわかることを質問しない。逆に、要件・好み・トレードオフの選択は
  勝手に仮定せず、明示して確認するか、仮定を明記して進む。
- **決定台帳を保つ。** 長いタスクでは「決定済み（と根拠）／未解決／却下（と理由）」を
  頭の中で明確に分ける。決定済みを蒸し返さない。却下した案を理由ごと忘れて再提案しない。
- **同じ失敗を3回繰り返したら戦略を変える。** リトライではなく、前提を疑う。
  「このアプローチ自体が間違っている可能性」をその時点で必ず一度検討する。

## 4. 認識の衛生（epistemic hygiene）

- **パターンマッチと推論を区別する。** 「よくあるエラーに似ている」は仮説の生成には使えるが、
  結論には使えない。この事例固有の証拠で裏づけてから動く。
  特に、状態を変える操作（再起動・削除・設定変更）の前は、症状の一致だけで実行しない。
- **確信度を正直に運ぶ。** 観測した事実／推論した結論／置いた仮定を混ぜて報告しない。
  失敗は失敗と、スキップはスキップと報告する。うまくいっていない状態を進捗のように語らない。
- **簡単な説明から検証する。** 複雑で知的に面白い仮説より、typo・キャッシュ・
  設定ミス・バージョン違いのような退屈な原因を先に潰す。

## 5. 作業ループ

すべてはこの反復に収束する：

```
理解する（未知を列挙）
→ 最もリスクの高い未知を潰す最小の一手を選ぶ
→ 実行前に結果を予測する
→ 実行し、予測と照合する
→ ズレがあればモデルを修正、なければ次の未知へ
→ 完了条件を観測可能な事実で満たしたことを確認して終了
```

完了の宣言は「やった」ではなく「観測した」に基づくこと。
最後のメッセージには、何を確認済みで、何が未検証のまま残っているかを必ず含める。

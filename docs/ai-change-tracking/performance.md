# AI Change Tracking: ベースラインと記録の計測 (M104d2)

追跡サービス (`tools\track`、`mye_track.exe`) のベースラインと記録のスループットを、計測してから軽くした記録。
AGENTS.md §3.5 (推測で最適化しない) に従い、先に計測し、遅い箇所だけ直した。目標値は置かない (architecture.md §11)。
取りこぼしの検出 (検証の走査) の設計は [architecture.md](architecture.md) §4。

## 1. 取り直す手順

release ビルドで測る。**追跡対象は読むだけ**で、記録の置き場所 (`.mye\ai_changes\` の代わり) は `--data` で別のディレクトリへ向ける。リポジトリの作業ツリーと `.mye` は書かれない。

```
cargo build --release --manifest-path tools\track\Cargo.toml

# (a) このリポジトリのベースライン (リポジトリのルートで実行。読むだけ。--data は一時ディレクトリ)
tools\track\target\release\mye_track.exe bench baseline --project . --data %TEMP%\mye_bench_data

# (b) 生成した 32000 ファイル (小さなテキスト。256 本ずつのディレクトリ)
tools\track\target\release\mye_track.exe bench gen --dir %TEMP%\mye_bench_gen --files 32000
tools\track\target\release\mye_track.exe bench baseline --project %TEMP%\mye_bench_gen --data %TEMP%\mye_bench_data2
tools\track\target\release\mye_track.exe bench changes --project %TEMP%\mye_bench_gen --data %TEMP%\mye_bench_data3 --counts 1,1000,32000
```

- `--data` のディレクトリは、実行ごとに消してから使う (残っていると 2 回目以降の突き合わせになり、ベースラインを測れない)。
- `bench baseline` が出すもの: ベースラインの所要時間 (`baseline_total_ms`)、ファイル数、元の総量、内訳 (`walk_ms` = 走査、`read_ms` = 読み取り、`hash_ms` = SHA-256 とテキスト判定、`commit_ms` = Writer へ渡して戻るまで)、Writer の中の内訳 (`blob_*` = Blob の `put`、`journal_append_ms`、`event_insert_ms`、`snapshot_insert_ms`、`tx_commit_ms`)、Blob の本数と総量 (重複排除の後)。Writer の内訳は別スレッドの累計で、`commit_ms` の中身。
- `bench changes` はベースラインの後、`--counts` の件数ずつ内容を書き換え、全部の Revision が `tracking.db` に出るまでの時間を測る。1 件は 5 回測って個別に出す。`total_ms` はデバウンス (300 ms) と書き手の待ち (`settle_wait`) を含む。`write_ms` は書き換えそのものの時間 (測る側の書き込みで、追跡の性能ではない)。書き換えの内容は実行ごとに変える (前の実行が書いた内容と同じだと、変更にならない)。
- `.mye\ai_changes\` をリポジトリの外へ向ける口は `StartupOptions::data_dir` (`Paths::at`)。`serve` は従来どおり `<project>\.mye\ai_changes\`。
- **値は揺れる。** 他のプロセス (ウイルス対策のスキャンを含む) の影響を受け、同じ版で同じ手順でも、時間帯で 2 倍以上違った (下)。値は同じ時間帯の前後比較に使い、プロセス内の累計 (Blob の内訳) を判断の根拠にした。

### 判断

- **直した 1: Blob 1 件ごとの `sync_all` をやめた。** 前の 231.6 秒のうち 151.4 秒 (65%)。やめた版は 72〜75 秒。「全部書いてから、開き直して 1 回ずつ `sync_all`」(まとめて同期) も試したが、同期だけで 28.5 秒かかり合計 92.5 秒で、やめるより遅い。電源断で起こりうること (最終名のまま中身が欠けた Blob) は、起動時に直近の Blob の内容を確かめて見つける (db-schema.md §4、§6 の 3 の前段。試験 `startup_finds_corrupt_recent_blob_and_marks_it_missing`)。
- **直した 2: 書いた Blob の読み直しを、書いたハンドルで行う。** 閉じて開き直す方式は、`sync_all` をやめた後に 34 秒から 50 秒へ増えた (書いたばかりのファイルを OS が開き直しの時点で検査すると見られる。原因は断定していない)。書いたハンドルを先頭へ戻して読む方式は、その直後の別の 1 回 (他は同じ版) で 5.5 秒 (全体 36.9 秒)。検証の意味 (読み直した内容のハッシュが合ったときだけ最終名へ rename する) は変えない。どちらも OS のキャッシュを読む。
- **直した 3: `put` が内容のハッシュを取り直すのをやめた** (走査が取ったハッシュを `put_hashed` へ渡す。渡したハッシュが内容と違えば、読み直しの検証が落ちる)。直前の版と連続して測り、`commit_ms` が 11096〜11790 から 8482〜8913 へ (約 2.7 秒)。
- **直さなかった**:
  - ディレクトリの確認 (`create_dir_all`) を省く (作ってみてから失敗したときだけ作る): 32000 本では全体の 17% (12.4 秒) を占めていたが、省くと作成と rename の時間がその分増え、全体は 75 秒 → 72〜75 秒と変わらなかった (連続した 3 回)。効果が測れないので戻した。
  - 走査の `hash_ms` (2.6 秒) と読み直しのハッシュ: 読み直しは検証そのもので省けない。走査のハッシュは Blob 名と `snapshots` の元になる。
  - ベースライン全体を並列にする: Writer の直列化 (architecture.md §3.1) を崩すので、計測の結果ではなく設計の理由で採らない。
  - 一時ファイルを使わず最終名へ直接書く (rename を省く): 小さいファイルが多い 32000 本では rename が 3 分の 1 だが、「最終名にあるものは検証済み」という不変条件 (既存確認が大きさだけで済ませている根拠。db-schema.md §4) を崩すので採らない。
- 結果として、このリポジトリのベースラインは **約 12〜35 秒** (前: 約 232 秒)。分単位で終わらない状態ではない。

## 4. 生成した 32000 ファイル (小さなテキスト、元の総量 7.4 MB)

直した 3 の前の版 (この条件では `put` のハッシュが 0.2 秒で、結果は変わらない)。`bench baseline` を 2 回 (別の時間帯にも 3 回)、`bench changes` を 1 回。

| 項目 | 値 |
|---|---|
| ベースライン全体 | 95277、103441 (時間帯を変えた別の 3 回: 71646、75211、74930) |
| └ 走査 / 読み取り / ハッシュ | 53〜61 / 7916〜8724 / 93〜94 |
| └ Writer への依頼 | 86342、95308 |
| └ Blob の作成と書き込み / rename / `create_dir_all` / 既存確認 | 18375〜21744 / 33931〜49953 / 12819〜14806 / 3596〜4017 |
| └ `snapshots` の INSERT / COMMIT / 読み直し | 2500〜2793 / 965〜1058 / 1650〜1851 |
| Blob 本数 (重複排除後) / 総量 | 32000 本 / 7396890 B |
| 1 件の変更が `tracking.db` に出るまで (5 回) | 422、423、425、425、474 ms (デバウンス 300 ms と書き手の待ち 100 ms を含む。残りの約 25 ms が記録) |
| 一括 1000 件 | 3723 ms (268 件/秒、書き換えそのものに 1689 ms) |
| 一括 32000 件 | 139940 ms (229 件/秒、書き換えそのものに 61961 ms) |

- 32000 本のベースラインは **1 分半〜2 分弱**。1 本あたり 2〜3 ms で、内訳は Blob 1 本ごとのファイル作成・rename・ディレクトリの確認 (NTFS のメタデータ操作) が 8 割。小さいファイルが多い場合に残るのはここで、直すなら多数の小さな Blob を 1 つのファイルにまとめる (パック) ことになる。保存形式と復元の経路が変わるので、このサブでは扱わない。
- 一括 32000 件のうち、書き換えそのものに 62 秒かかっている (測る側の書き込み)。追跡は書き換えの終わりから約 78 秒後に全件を記録した。Writer の累計は 32000 件あたり約 90 秒 (1 件 2.8 ms、秒あたり約 355 件が上限)。前の実装は、別の条件 (debug ビルド、他の負荷あり) で約 40 件/秒だった (sub-03 の記録)。
- 1 件の記録は debounce を除くと 25 ms 程度で、体感の遅れは debounce (300 ms) が決める。

## 5. 取りこぼしの検出の実測

- `notify` 8.2.2 は Windows で本物のバッファあふれを報告しない (architecture.md §4)。検証の走査 (architecture.md §4) を入れる前、32000 件の一括書き換えを測ったところ、検証の走査が「23242 件の違い」を見つけた。調べると、長い flush の間に溜まった処理待ちのイベント (取りこぼしではない) を、走査が取りこぼしと取り違えていた。走査の前にキューを空にする修正を入れ、試験 `backlog_of_unprocessed_events_is_not_mistaken_for_a_miss` を足した (修正を外すと 3 回中 2 回落ちる)。修正の後の 32000 件の一括書き換えは、`gap` が 0 件で全件が通常の経路で記録された。
- 16 スレッド × 4000 ファイル (計 64000) の試験 `real_overflow_is_fully_covered_after_verification` (`#[ignore]`) の結果は §6。

## 6. 本物の取りこぼし (16 スレッド × 4000 ファイル)

`cargo test --release --test reconcile -- --ignored --nocapture` の試験 `real_overflow_is_fully_covered_after_verification`。16 スレッドが長い名前の小さなファイルを 4000 本ずつ (計 64000) 書き、検証の走査が 2 回以上終わるまで待つ。

- 書き込み 78.8 秒。**検証の走査が 2693 件の取りこぼしを見つけた** (`notify` が届けなかった作成。`Err` も再走査フラグも出ていない)。`gap` の Revision 2693 件、`watcher_overflow` の区間 1 件。記録は 64000 / 64000 で、記録の無いファイルは 0 本。全ファイルの最後の Revision の After が実際の内容と一致した。経過 315.0 秒 (試験全体 365.8 秒)。
- 取りこぼし率は、sub-03 の使い捨ての試験 (約 6900 / 64000) と同じ桁。取りこぼしが起きなかった回は区間が残らず、全件が通常の Revision になる (試験は両方を許す)。

## 7. 検証の走査だけの所要時間 (M104f)

`status` が直近の検証の走査の前半 (`detect_changed` = 歩いて、サイズと更新時刻を突き合わせる) だけの所要時間を `verify.lastScanMs` に出す (内容は読まない。後半の読み取りと、イベントの遅れを待つ時間は含まない)。

手順 (リポジトリの `.mye` を汚さないため、作業ツリーのコピーで測った):

```
robocopy C:\HAL\MyEngin %TEMP%\mye_vscan /E /XD .git bin obj .mye cache target .vs
mye_track.exe serve --project %TEMP%\mye_vscan          # phase = watching まで待つ
# 小さいファイルを 1100 本作る (検証の走査の起動条件 = 前回の走査の後に 1000 件のイベントが溜まる + 3 秒の静けさ)
mye_track.exe client --project %TEMP%\mye_vscan          # hello + status を流す (tools\track_verify.ps1 の Invoke-Raw が見本)
```

- 2026-11-15、§2 の環境、release ビルド、この版のコピー (追跡対象 3005 ファイル、551 MB)。ベースラインは 33.3 秒 (走査 0.2 秒、読み取り 22.6 秒、ハッシュ 2.4 秒、Writer への引き渡し 7.5 秒)。
- 1100 本を足して追跡対象が 4105 ファイルになった後の検証の走査 (前半だけ): **615 ms** (1 回)。ファイルの数に比例する歩く + stat の時間で、内容を読まない。5 分おきの走査として許容範囲。32000 ファイルでの値は未測定 (ファイル数の比で数秒と見込むが、推測)。
- 1 件の記録 (`status` の `recent.recordUs`): 観測 1 件あたり Writer への往復 1.6 ms (1100 件を 1 回で渡した平均)。
- 計測の後始末: コピーとサービスのプロセスは消した。リポジトリの `.mye` は作られていない。

## 8. 洪水と取りこぼし: 監視を分ける (M104g2)

`notify` の Windows 版は、`watch()` ごとに別のハンドルと 16 KiB のバッファを持ち、あふれを報告しない (architecture.md §4)。ルートを再帰 1 本で見ていた版は、無視するディレクトリ (`bin` / `obj` / `target` / `.git` など) の書き込みの洪水が、追跡対象と同じバッファを取り合った。測ってから、監視を分けた。

### 8.1 取り直す手順

release ビルドで測る。作業ディレクトリは**新しく作る** (あるものは使わない。測る側が消さないので、終わったら自分で消す)。追跡対象を測る側が書くのは、その作業ディレクトリの中だけ。

```
cargo build --release --manifest-path tools\track\Cargo.toml

# 実測 A: 洪水と編集の重なり。無視される bin\ へ 16 スレッドが計 64000 ファイルを書く間に、追跡対象の src\s*.txt を 200 回 (50 ms 間隔) 1 つずつ保存する
tools\track\target\release\mye_track.exe bench flood --dir %TEMP%\mye_flood_a --flood-dir bin --load 24
#   --flood-dir src/sub/target  入れ子の無視ディレクトリ
#   --load N                    CPU を使い続けるスレッドを N 本 (同じプロセス内)。0 = なし

# 実測 B: 追跡対象 2500 ファイルの一括作成 (sub-06 で取りこぼしを再現した条件)
tools\track\target\release\mye_track.exe bench burst --dir %TEMP%\mye_burst_b --files 2500
#   別プロセスの CPU 負荷: mye_track.exe bench load --threads 1 --secs 600 を 24 本起動しておく。4 本同時に burst を回す

# このリポジトリでの監視の分け方 (監視は張らない。読むだけ)
tools\track\target\release\mye_track.exe bench plan --project .
```

- `flood` / `burst` は、検証の走査を短い間隔 (静けさ 1 秒、間隔 2 秒) で回す設定で動かす (取りこぼしの数には影響しない。待ちを短くするだけ)。`tracked_normal` は通常の Revision (`complete` / `coalesced`)、`tracked_gap` は検証の走査が拾った `gap` の Revision、`tracked_missing` は記録が無いもの。
- 環境は §2 と同じ (6 コア 12 スレッド)。値は揺れる。2026-11-15 に測った。

### 8.2 結果

実測 A (追跡対象 200 件のうち。洪水 64000 ファイル、16 スレッド、各条件 3 回):

| 条件 | 前 (ルート再帰 1 本) | 後 (分ける) |
|---|---|---|
| `bin\`、CPU 負荷なし | 通常 200 / `gap` 0 (3 回とも) | 通常 200 / `gap` 0 (3 回とも。監視 2 本) |
| `bin\`、CPU 負荷 24 スレッド | `gap` **8、15、12** (通常 192、185、188。`watcher_overflow` の区間 1 件ずつ) | `gap` **0** (3 回とも。監視 2 本) |
| 入れ子 `src\sub\target`、CPU 負荷なし | (前は同じ形。`bin\` と同じ) | `gap` 0 (3 回とも。監視 3 本) |
| 入れ子 `src\sub\target`、CPU 負荷 24 スレッド | `gap` **9、21、8** (通常 191、179、192) | `gap` **0** (3 回とも。監視 3 本) |

- 「前」の負荷なしが 0 件なのは、洪水が速いだけでは足りず、読む側が CPU を取れないことが条件だから (sub-06 の調査と合う)。**推測は当たっていた**: 洪水が無視するディレクトリにあるだけで、追跡対象の `gap` が出た。
- 「後」は、洪水のイベントが追跡対象の監視の外にあるので、追跡対象の監視 (ルート非再帰 + `src` ほか) のバッファには入らない。入れ子の無視ディレクトリも、親を「非再帰 + 無視しない子を再帰」に分けて外した (`src` と `src\sub` が非再帰、`src\sub\target` は監視しない)。
- 受け入れ条件 2 は、全 12 回 (4 条件 × 3 回) で 0 件だった。

実測 B (追跡対象 2500 ファイルの一括作成):

| 条件 | 結果 |
|---|---|
| 前 (release)、4 本同時、プロセス内の CPU 負荷 6 スレッド × 4 | 12 回とも記録 2500 / `gap` 0 |
| 前 (release)、4 本同時、別プロセスの CPU 負荷 24 本 | 8 回とも記録 2500 / `gap` 0 |
| 後 (release)、4 本同時、別プロセスの CPU 負荷 24 本 | 8 回とも記録 2500 / `gap` 0 |
| 後 (debug ビルド)、4 本同時、別プロセスの CPU 負荷 24 本 | 8 回とも記録 2500 / `gap` 0 |

- **sub-06 で見えた「2500 件のうち 54〜130 件が届かない」を、この計測の道具では再現できなかった** (上は計 36 回、すべて 0)。sub-06 は `cargo test` の試験 (`bulk_writes_are_each_recorded_once_as_a_normal_or_a_gap_revision`) を 4 本同時に動かしていて、書き込みの方式 (1 ファイルずつディレクトリを作り直す確認を挟む) と動かし方が違う。取りこぼしが確率的なので、起きない条件を見つけたのであって、起きないことの証明ではない。
- B の対象は 1 つのディレクトリへの一括作成で、**監視を分けても変わらない** (そのディレクトリの監視は 1 本のまま)。つまり B の取りこぼしがあれば、残る限界。検証の走査 (sub-21) が `gap` として拾う (記録は欠けない)。

### 8.3 自前の `ReadDirectoryChangesW` (第 2 の手) は入れなかった

- 実測 A は分けた後に 0 件、実測 B は計測の道具で再現できず実用上の数が無い。**入れる根拠 (実測の値) が無い。**
- sub-06 の試作 (1 MiB バッファ、あふれ検出、重ねた I/O) は「バースト直後の最初の 3〜4 件が届かない」欠陥の原因を突き止められないまま取り除かれた。原因を突き止められないものを製品に入れない (sub-22 の方針)。
- B の取りこぼしが実際の使い方で問題になると分かったときの次の手として残す (architecture.md §4 の「残る限界」)。

### 8.4 監視の本数

- このリポジトリ (`bench plan --project .`): **76 本** (非再帰 20、再帰 56)、計画づくり 46 ms。上限は 256 本で、超えたらルートの再帰 1 本へ戻して `status` の `watches.fallback` に出す。
- 付け替えは、ディレクトリの出入りと `.gitignore` の書き込みで起きる。ディレクトリを大量に作る間は、最短 200 ms 間隔、直近の計画づくりの 8 倍の時間より短くは空けない。

## 9. シーン構造 diff (M104l)

計測の手順 (release。測る前に他のビルドを止める):

```
cargo test --release --manifest-path tools\track\Cargo.toml --test scene_diff -- --ignored --nocapture --test-threads=1
```

- 入力: エンティティ 2 万個のシーン (1 エンティティ 2 コンポーネント、1 文書 4.87 MB、Before と After)。1000 個ごとに 1 フィールドを変えた (変更 20 件)。
- **構造比較 (純粋な関数 `scene_diff::diff`)**: 約 160 ms (162.9 ms、1 回)。字句を保つ読み (2 回分) + `fileId` の対応付け + 比較で、入力の大きさにほぼ比例する (エンティティごとに同じ字句なら比較せず通す)。
- **Tracker を通した記録** (監視 → Diff ワーカー → Writer): シーンを書いてから Revision が確定するまで約 540 ms (デバウンス 150 ms と書き手の待ちを含む)。同時に書いた小さなファイル (`other.txt`) は同じ約 540 ms で確定した (構造比較は Diff ワーカーの中で、Writer のキューを止めない。Collector は比較が終わるまで次のバッチを渡さないが、2 万個で 0.2 秒未満)。
- 環境は §2 と同じ (1 回の計測。値は揺れる)。上限 (1 文書 8 MiB、行 diff の合計上限の半分) までの入力でも比例の範囲。

## 10. 大きいシーンの表示側の計測と、プレハブ伝播 (M104t)

AGENTS.md §3.5 に従い、先に測り、遅い箇所だけ直す。環境は §2 と同じ (2026-11-16、Release、6 コア 12 スレッド。値は揺れる)。

### 10.1 取り直す手順

```
# Editor 側 (Release。作業ディレクトリはリポジトリ。リポジトリの .mye も imgui.ini も書かない)
#   20000 エンティティのシーン (親 200 x 子 99 + 親)。変更済みを 10 / 1000 / 20000 件にして、表示側の費用を測る
set MYE_SELFTEST_ONLY=changetracking
set MYE_CHANGETRACKING_PERF=1
bin\x64\Release\Editor.exe --selftest
#   出力の "[perf] changed=" の行 (環境変数が無いときは何もしない)

# サービス側 (scene_overlay の応答、プレハブ伝播の費用)
cargo test --release --manifest-path tools\track\Cargo.toml --test propagation -- --ignored --nocapture --test-threads=1
# 構造 diff (§9)
cargo test --release --manifest-path tools\track\Cargo.toml --test scene_diff -- --ignored --nocapture --test-threads=1

# 監視の分け方の計画づくり (数万ディレクトリ。測る側が作った一時ツリーで。監視は張らない)
tools\track\target\release\mye_track.exe bench plan --project <30200 ディレクトリのツリー>
```

- Editor 側の計測はヘッドレスで、描画 (GPU) と実際の `Poll()` の pipe 読み取りは含まない。偽の I/O が返事を渡すので、`maxPoll` は「返事 1 ページを解析して表に入れる」費用 (OS の pipe の待ちを除く)。**1 フレームの合計の増分は測っていない** (ヘッドレスでは Scene View を描かない)。代わりに、毎フレーム走る部分 (Hierarchy の描画、Scene View の候補作りと選び方) を個別に測った。
- 1 ページは、この試験では約 1900 エンティティ (約 0.6 MB) で、サービスのページの予算 (768 KiB) に近い。

### 10.2 結果

| 項目 | 10 件 | 1000 件 | 20000 件 |

| └ `Poll()` 1 回 (返事 1 ページ。最大) | 0.17 | 15.8 | 31〜32 (約 0.59 MB) |

| `RebuildAncestors` (取り直しのあと 1 回) | 0.14 | 14.6〜16.1 | 280〜311 |

| Scene View の候補作り (毎フレーム、`FindByFileId` 込み) | 0.001 | 0.08〜0.09 | 3.0〜4.6 |
| Scene View の選び方 (毎フレーム、見えている順に並べて 256 件まで) | 0.000 | 0.04〜0.05 | 1.2〜1.3 |
| Hierarchy の 1 フレーム (ヘッドレス、追跡あり / なし) | 0.45〜0.54 / 0.42〜0.57 | 0.31〜0.34 / 0.21〜0.23 | 0.31〜0.34 / 0.22〜0.24 |

- **取り直しは 1 ページごとに JSON を解析するのが主で、表の解析 (`ParseEntities`) は 2〜3 割**。20000 件は 1 ページ 31 ms (約 2 フレーム) の引っかかりになりうるが、変更が 2 万件ある文書は極端な場合。1000 件までは 1 ページ 16 ms 以下。
- **`RebuildAncestors` と最初の候補作りの 280〜311 ms (20000 件)、14.6〜16 ms (1000 件) は、`FindByFileId` の最初の 1 回ずつが全エンティティの線形走査だから** (`Scene::fileIdCache_` は採番点でしか温まらず、読み込んだシーンでは空。同じ fileId の 2 回目からは 2 ms / 2 万件)。切り分け: 同じシーンで `FindByFileId` を 2 万回続けて引くと、1 周目 295 ms、2 周目 2.1 ms。`getParent` と `FileIdComponent` の取得は 2 万回で 0.2 ms 以下。これは Engine 層 (`Scene.cpp`) の性質で、Editor 側だけでは消せない (下の「直さなかった」)。

### 10.3 判断

- **可視の判定を AABB にするか: 変えない。** 現在の判定は原点 (ワールド行列の移動成分) だけで、画面の端から 1.5 倍の余裕で拾う (`ProjectChangePoint`)。AABB の 8 隅を同じ関数に通す見積もりの追加は、1000 件で 0.13〜0.15 ms、2 万件で 2.5 ms (毎フレーム)。これに加えて、エンティティごとにメッシュの境界を引く費用 (アセットの検索。メッシュの無いエンティティにはそもそも境界が無い) が要る。原点だけで外れるのは「原点は画面の外で、大きいメッシュだけが見えている」場合で、そのときは 1.5 倍の余裕で拾えることが多い。拾えない場合は箱が出ない (ツリー・Hierarchy のバッジとは独立)。測った費用に対して見合う利益 (取りこぼしの実例) が無いので変えない。変えるなら、ワイヤ箱・ゴースト・ピック・重ねの印の 4 か所を `ProjectChangePoint` の 1 か所で同じ判定にする。
- **`FindByFileId` の初回の線形走査: 直さなかった。** `RebuildAncestors` を「全エンティティを 1 回だけ走査して表に当たったものだけ親をたどる」に書き換えると、`RebuildAncestors` は 280〜311 ms → 2.4〜3.2 ms (20000 件)、14.6〜16 ms → 0.6 ms (1000 件) になった。しかし直後の Scene View の候補作りの最初のフレームが同じ線形走査を払い直す (最初の候補作り 280〜308 ms / 14.5 ms)。合計の引っかかりは変わらないので書き換えを戻した (測って、利益が無いと分かった変更は入れない)。解消するには、読み込み時に `fileIdCache_` を温める (Engine 層の `Scene` / シリアライザ) か、Editor が全エンティティの走査を 1 か所で 1 回だけ行い、その結果を Hierarchy・Scene View・ゴーストの全部が共有する必要がある。後者は変更の範囲が広いので、別サブの候補にする (1000 件までの引っかかりは約 15 ms)。
- **`scene_overlay` の全ページ再畳み込み (20000 件で 1.1 秒) と 1 ページの JSON の解析 (31 ms): 直さなかった。** Editor のフレームを止めるのは `Poll()` の解析だけで、1000 件までは 16 ms 以下。極端な場合 (変更 2 万件) のための作り直し (畳んだ結果の保持、小さいページ) は、そういう文書が実際に出てから。
- 伝播の計算の費用は約 6 ms (100 シーン) で、対象のシーンを文字列で絞ってから JSON として読むため。上限 (読むシーン 300、合計 256 MiB、1 シーン 16 MiB、出す行 20000) は超えたとき打ち切って件数を残す。上限そのものの超過時の所要時間は測っていない。

### 10.4 性能の目標値

arch §11 に置く。値は上の計測を根拠に、余裕を持たせた:

- 表示側 (毎フレーム): 変更 1000 件までで、Scene View の候補作りと選び方の合計が 0.5 ms 以内、Hierarchy の描画に追跡の有無の差が出ない。
- 取り直し 1 ページの `Poll()` は 1000 件までのページで 20 ms 以内 (2 万件の 1 ページは 31 ms で、これは目標の外)。
- 1 回の初回の `FindByFileId` による引っかかり (取り直しのあとの 1 回): 1000 件までで 20 ms 以内 (2 万件では 300 ms で、目標の外)。
- 記録: 1 件の変更が `tracking.db` に出るまで、デバウンスを除いて 30 ms 前後 (§4)。大きいシーンの構造 diff は 2 万エンティティで 200 ms 以内。
- プレハブ伝播の計算: 100 シーン x 100 インスタンスで 50 ms 以内の増分。
- `scene_overlay` の応答: 変更 1000 件までで 50 ms 以内 (20000 件は 1.1 秒で、これは目標の外)。

# ADR-011: 構成定義アセット (.actor.json) = プレハブ 2.0

## 決定

- ユーザー起草の「構成定義アセット 仕様書 v1」を、**新規システムではなく既存プレハブ (M13) の
  拡張**として実装する。上書き機構・ライブラリ・タグ・インスタンス化はすべて共通で、
  `.prefab.json` は「単一ルート・部位なし・overrides なし」の**部分集合として読込互換**にする
- GUID は既存の **64bit パスハッシュ + `.meta`** を流用する (UUID は不採用)
- ローカル ID は fileId 規約 (u64、単一ルートなら root=1)
- **シーン配置 = 「展開 + override リスト併記」**。ロードは展開値をそのまま使い (決定論安全)、
  そのあと**非上書きフィールドだけ**をベース最新値へ更新する
- **部位 (ソケット) = `PartComponent` を持つ子エンティティ**。特別な構文は作らない。
  ボーン追従は v1 で完全対応し、当たり判定のひも付けは v1 外
  (→ **M49 の `PartBoundsComponent` (箱/球ボリューム) + `RaycastParts` で回収済み**)
- 部位を引く手段だけを C ABI に足す (`FindPart` / `FindPartsByTag`)。取り付けは既存 `SetParent`
- スキーマ (`*.component.schema.json`) による**動的コンポーネント登録**を持つ。
  コード生成 (C++ typed struct / C# ミラー) は M49 以降
  (→ **M50d の汎用フィールド ABI v11 + スキーマ codegen で回収済み**。下の追記参照)
- アセットは**専用の Scene に展開して編集**する (ミニシーン編集モード)

## 理由

### なぜ「新システム」ではなく「プレハブ 2.0」か

仕様書の中身を既存機能と突き合わせると、真に新しいのは
**タグ / 部位 / 入れ子 / 保存型 overrides / スキーマ**の 5 つだけで、
アセット形式・ライブラリ・インスタンス化・ホットリロード・Inspector 統合は M13 のプレハブに
すでにあった。別系統を建てると「プレハブとアクターのどちらで作るのか」が全編集フローに
分岐として残り、上書き機構が 2 つになる。**上書きの実装が 2 本ある状態が最悪**なので、
拡張として 1 本に統合した。

### なぜ overrides を「保存型」にしたか (M48e)

M13 は上書きを保存せず、**ライブ diff** (現在値 != ベース値) で判定していた。これは
「シーンを閉じている間にベースが変わった」場合に誤判定する:

- ベースを A→B に変えると、上書きしていないフィールドまで「ベースと違う = 上書き」に見える
- 逆に、上書きした値がたまたま新ベースと一致すると上書きが消える

つまりライブ diff が正しいのは「ベースが現行と一致していると分かっている瞬間」だけ。
そこで**その瞬間にスナップショットを撮って保存する**方式にした。撮る場所は
`UndoStack::CaptureAfter` の 1 箇所 (全エディタ編集経路の共通出口) + ベース更新直後 +
レガシー移行時の 3 つ。記録の無いインスタンスはライブ diff にフォールバックするので、
**既存シーンはビット単位で不変のままロードできる**。

### なぜ入れ子は「再帰インスタンス化」ではないか (M48c)

プレハブは**展開保存**される — シーンにもアセットにもメンバの実体が丸ごと入っている。
だから入れ子で必要なのは再帰的な生成ではなく、**境界を尊重したタグ付けと列挙**だけだった。
規約は 3 つ:

1. `PrefabLink.localId` は**自分が直接所属するインスタンスのベース**のドメインの値。
   内側インスタンスのメンバは内側ベースの番号を保つ (参照ではなくデータなので remap 不要)
2. 内側ルートは `PrefabInstance{prefabHash=内側, outerLocalId=外側での位置}` と
   `PrefabLink{localId=1}` (内側ドメイン) を同時に持つ
3. 所属境界は `FindInstanceRoot` (最近祖先) が唯一の定義。列挙・抽出・タグ付けを全部そこに揃える

「代理指標で境界を判定する」実装 (深さ、名前、タグの有無…) を作らないことが肝で、
番号の使い回しは即データ破壊になる。

### なぜ部位は「エンティティ」なのか

ソケットを専用の軽量構造体にすると、Transform・親子・シリアライズ・Inspector・ギズモを
全部作り直すことになる。エンティティにすれば**既存機構がそのまま全部効く**。
コストは「エンティティが増える」だけで、部位は数個〜数十個の世界なので問題にならない。

### なぜ ABI に足したのが 2 本だけなのか (M48h)

本命ユースケースは `SetEffect(leg)` = 「アセットが決めた場所にランタイムが物を付ける」。
分解すると **引く** (どこ?) と **付ける** (SetParent) で、後者は v3 からある。
瞬間位置も既存の Transform getter で取れる。だから増やしたのは引く手段だけで、
残りは `ScriptAPI.h` / `MyeScript.cs` の糖衣にした。ABI は末尾 append 専用で
`Interop.cs` が位置ベースにミラーしているため、**足す本数を減らすこと自体が安全側**。

### なぜスキーマは「コード生成なし」から始めたか (M48j)

`FieldType` は閉集合 15 種で、Inspector・シリアライザ・ワールドハッシュ・DLL 移行の
4 者が同じメタデータを見ている。つまり **`ComponentDesc` を実行時に組み立てられれば
UI コードは 1 行も要らない**。コード生成 (型付きアクセサ) はその上に載る別の層なので、
先に「登録・オーサリング・保存・ハッシュ被覆」を通した。

決定論の契約は登録位置に集約した: **組込み型の後・スクリプト型の前**の 1 箇所で、
相対パス昇順に登録する。こうするとスキーマ型は連続ブロックになり、スクリプト型の TypeId は
一様にずれるだけで**エンティティ内の相対順が変わらない** = 既存シーンのハッシュが動かない。
(M48i のバイナリで録った golden.rep が M48j のバイナリで 600 tick 一致することで実測した)

### なぜミニシーン編集モードは「Scene ポインタの差し替え」なのか (M48k)

M13 では「`ctx.scene` を差し替えるのは危険」として編集モードを見送っていた。
実際に危ないのは **tick 経路**で、`ScriptHost` / `ManagedHost` / `ReloadHub` は Init 時に
`Scene*` を捕まえ、`EngineLoop` はローカルの Scene を直接触る。
一方 **エディタ側は全部が引数駆動** (`Hierarchy` / `Inspector` / `SceneView` / `UndoStack` /
`Selection` / `SceneSerializer` はすべて `Scene&` か `EngineContext&` を受け取る)。

そこで差し替えを **`EditorApp::OnImGui` と `OnRenderViews` の中だけ**に閉じた。
tick 経路には触れないので、スクリプトも物理もリプレイも編集モードの存在を知らない。
`selection_` / `undo_` は**中身ごと入れ替える**ことで、EditorApp 内 49 箇所の参照を
1 つも書き換えずに「今開いている文書」を切り替えられるようにした。

## v1 の制限 (意図的に外したもの。★= その後回収済み)

- ★**構造変更の上書き** (`added` / `removed`) — **M50c で回収** (override キー
  `"+Component"` / `"-Component"` + シーン文書 v3。詳細は ADR-012)。
  エンティティ (= 子) の増減の追跡は引き続き v2 (コンポーネント単位のみ)
- **3 層マージなし**: 外側ベースが内側ルートに掛けた変更は再伝播しない
- ★**当たり判定のひも付けなし** — **M49 で回収** (`PartBoundsComponent` の箱/球ボリューム +
  SceneView クリック選択 + `Parts::RaycastParts` / ABI v10)
- 名前の一意化は**エディタ操作時のみ** (ロード / ランタイムには適用しない = 既存シーン不変)
- 骨追従の部位は **source の直子**に置く規約。gWorld 補間とボーンパレット非補間の差で
  追従部位の描画が最大 1 tick ずれるのは容認
- Runtime からのタグ名逆引き非対応 (ID のみ)。C# 部位 API は**リプレイ被覆外** (別レーン)
- ★スキーマの**汎用フィールド ABI / 型付きコード生成なし** — **M50d で回収**
  (下の追記参照)。残る制限: **ホットリロードなし** (起動時 1 回)、1 プロセス 64 型まで
- 編集モードは **Play 無効・入れ子編集なし・GameView は常に本シーン**

## 回収した M13 の宿題

M13 (プレハブ) の「後で拾う」に挙げていたもののうち、本 ADR で回収したもの:

| M13 で見送った項目 | 回収したサブ |
|---|---|
| 分離ステージのプレハブ編集モード | M48k (ミニシーン編集モード) |
| ネスト (入れ子プレハブ) | M48c (ID ドメインの分離) |
| コンポーネント追加/削除の Revert | M50c (構造上書き + シーン文書 v3。ADR-012) |
| Unpack Prefab | M50b (`Prefab::UnpackInstance` + 確認モーダル) |
| Asset Browser からの D&D 配置 | M15 後のアセット操作で回収済み |

## 影響

- **ReplayFile bump なし**。全追加が opt-in (新コンポーネント / 新キー / 新スロット) で、
  ハッシュアルゴリズムにも記録形式にも触れていない
- **ABI は v8 → v9** (M48h の 1 コミットに集約)。旧 `GameLogic.dll` は要再ビルド
- `replay_verify.bat` が **2 シーン被覆**になった (既定デモ + 部位ショーケース)。
  既定デモにはスキンメッシュが 1 体も無く、**骨演算は一度もハッシュ被覆に入っていなかった**

## 追記 (M49 / M50 での回収)

- **M49**: 範囲部位 = `PartBoundsComponent` (箱/球、末尾 append TypeId) + SceneView の
  ワイヤ表示/クリック選択 + `Parts::RaycastParts` (**ABI v10**)。「当たり判定のひも付け」が
  ここで回収された
- **M50b/M50c**: Create Prefab の命名/連番/Unpack と、構造上書き (コンポーネント
  追加/削除の Revert + シーン文書 v3 = ADR-012)。M13 宿題表の未回収 2 件が消えた
- **M50d**: スキーマの型付きコード生成。汎用フィールドアクセス
  `GetComponentField` / `SetComponentField` を **ABI v11** として追加し (型ごとの
  スロット増殖を避ける 2 本だけ)、生成物は
  `<project>\cache\Generated\SchemaComponents.gen.h` (レイアウトミラー + 型付きアクセサ +
  static_assert 検査) と `assets\scripts\Generated\Schema.gen.cs` (定数 + 型付きアクセサ)。
  入力は実行時レジストリそのもの — スキーマ JSON を再パースしないので
  **レイアウト計算の二重実装が存在しない**。nameHash は焼く / TypeId は焼かない。
  NoHash (C# スクリプト状態) レーンは ABI 側で読み書きとも遮断 (リプレイ保護)

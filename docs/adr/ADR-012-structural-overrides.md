# ADR-012: 構造上書き (コンポーネント追加/削除) とシーン文書 v3

## 決定

- プレハブインスタンスの**コンポーネント単位の構造変更**を override として追跡する
  (M50c)。エンティティ (= 子) の増減の追跡は引き続き対象外 (v2 のまま)
- override キーに `"+Component"` (インスタンスで追加) / `"-Component"` (インスタンスで削除)
  を追加する。`WriteEntity` / `ReadEntityOverrides` は任意文字列を素通しするので
  **ファイルフォーマット自体は変わらない**
- 構造キーは**ライブ diff から純導出**する (`OverridesAgainstBase` の拡張)。
  ベース走査で実体に無い → `-C`、実体アーキタイプ走査 (TypeId 昇順 = 決定論) で
  追跡対象かつベースに無い → `+C`
- 追跡述語は **`ReadEntityComponents` の removeMissing 除外集合のミラー**
  (NoSerialize / Hidden / Name / LocalTransform を除外、`kComponentScriptState` は含む)
- **シーン文書 version 2→3**。v3 は「キー不在 = ベース追随」を構造にも拡張する:
  ベースにあり実体に無く `-C` が無いコンポーネントは**ロード時に AddComponentRaw +
  ベース値充填**される (localId 昇順 = 決定論)
- 新 API: `Prefab::RevertComponent` (双方向) / `Prefab::ComponentOverrideState`
  (record 一次・ライブ fallback) / `Prefab::RemovedPrefabComponents` (Restore 一覧用)

## 理由

### なぜ「-C だけ」ではなく「+C」も必須か

`+C` の役割は削除の対 (対称性) ではなく**値クロバー防止**。インスタンスで追加した
コンポーネント C と同名の C をベースが後から獲得すると、`PropagateBaseChange` は
「非上書きフィールドをベース値へ更新する」規則に従って**インスタンスの値をベース既定値で
潰してしまう**。`+C` が付いていれば「このコンポーネントは丸ごとインスタンス由来」と
分かるので、値伝播をコンポーネントごとスキップできる。敵対的検証で「-C だけ」への
単純化は不成立と確認済み。

### なぜ純導出 (ライブ diff からの再計算) か

M48e の上書き記録は「編集の瞬間のスナップショット全置換」(`RecordOverrides`)。
構造キーだけ増分管理にすると、全置換とマージの 2 方式が同居して取りこぼしが
静かなデータ損失になる。導出をライブ diff の 1 箇所 (`OverridesAgainstBase`) に足せば、
既存の「撮る場所は `CaptureAfter` 1 箇所」という不変量がそのまま構造にも効く。

### なぜシーン文書の version を上げたか (最大の穴)

v2 の `RefreshNonOverridden` は「実体に無いコンポーネント」を扱えない。閉シーン中に
ベースへコンポーネントが追加されると、次に開いたとき実体に無い → ライブ diff が
「ユーザーの削除」と誤ラベル → `-C` が記録されて**恒久化**する。ユーザーは何もしていない
のにベース追加が永遠に届かない。これはフォーマットではなく**ロード時セマンティクスの
契約変更** (キー不在 = ベース追随を構造へ拡張) なので、version で区別する:

- **v3**: キー無し欠落はロードで補充 (ベース追随)。`+C` 付きはフィールド refresh を
  スキップ (クロバー対策)
- **v2** (M48e 期): 構造キーをライブ diff からレコードへ**マージのみ** (実体は変えない —
  旧アセットが「開いて保存しただけで変わる」のを防ぐ)。M48e 期の削除は `-C` を得て
  sticky 化 = 現行より改善。v2 + 閉間ベース成長は一度きり `-C` 扱い (明記済みの妥協)
- **レコード無し (レガシー)**: 現行移行のまま (拡張導出が構造キーも自動で拾う)

### 実装上の罠 (再発防止のため明記)

- `PropagateBaseChange` のループ内で `SetOverrides` が走るとリハッシュで
  レコードへの参照が失効する — **必ずコピーを取ってから参照する** (:1209 に同じ前例)
- Revert の構造復元 (Add/Remove) 後はアーキタイプ移動でコンポーネントポインタが変わる —
  再取得を忘れると別メモリを書く
- Inspector の Restore 節はエンジン内部の `ResolveBase` を引けないため、
  突き合わせ済みの一覧 API (`RemovedPrefabComponents`) をエンジン側に置いた
  (no-op 行を出さないのは API 側の責務)

## 制限

- 追跡は**コンポーネント単位のみ**。エンティティ (子) の追加/削除は追跡しない (v2 と同じ)
- ベース追加の C# コンポーネントは既定値で生える既存ギャップあり (スコープ外、
  コード内にコメント明記)

## 影響

- **ReplayFile / WorldHash / ABI bump なし** (override レコードはハッシュ対象外)
- 旧エンジンは `+/-` キーを素通しして不活性 (確認済み) — 前方互換
- UI: コンポーネントヘッダの「+」バッジ / 右クリック「Revert Added Component」/
  「Removed prefab components: [Restore]」節 (batchOp で Undo 一体)
- selftest 36 check + 変異テスト (復活抑止ゲート除去で 8 本 FAIL を実証して復元)

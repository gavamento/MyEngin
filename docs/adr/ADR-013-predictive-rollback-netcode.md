# ADR-013: 予測ロールバックのネットコード (2 人 P2P)

## 決定

- ネット対戦は **2 人 P2P の遅延ロックステップ + 予測ロールバック**とする (M52h / M52i)。
  3 人以上のメッシュ・リレーサーバ・NAT 越えは対象外 (M53 候補)。
- **ネット層は sim 状態を 1 バイトも書かない。** `NetSession` の役目は
  「tick T が消費するレーンを全 peer 分そろえること」だけ。
- 未着レーンは**直近の確定値の繰り返し**で予測して先へ進み、本物が届いて食い違ったら
  その tick の直前のスナップショットへ戻して再シムする。上限 **8 tick (133ms)**、
  超えたら stall (= M52h の素の遅延ロックステップへ縮退)。`--net-no-rollback` で常時そちらへ。
- 再シムは通常 tick と**同じ `RunOneTick`** を通す (決定台帳 2 / ADR-005)。
- **予測で走った tick は .rep に書かない / ハッシュも相手へ主張しない。**
  記録は `RunOneTick` の中から**確定処理**へ移し、「入力がもう覆らない」と分かった
  tick だけを追記する。
- desync 検出は **8 tick 刻みの checkpoint** で確定ハッシュを交換する。食い違ったら
  `crash\desync_<tick>_p<lane>\` にバンドル (.rep + フィールドダンプ + 手順) を吐いて
  **exit 4 で停止**する (`--net-no-halt-on-desync` で観察継続)。
- ABI v13 の `NetLocalPlayer` / `NetPingMs` / `NetRollbackCount` 等は**機種依存の値**。
  読むのは描画レーンに限り、sim 状態へ書かないこと。**禁止はしない — 検出する。**

## 理由

### なぜロックステップではなくロールバックか (そして両方残すか)

遅延ロックステップは「そろうまで待つ」ので、1 パケット落ちるたびにフレームが詰まる。
入力遅延を上げれば隠せるが、遅延そのものが操作感を殺す。ロールバックは待たない代わりに
「間違った未来を一瞬見せて、後から正す」— 8 tick = 133ms は人間が破綻と感じない範囲。

両方残したのは**切り分けのため**。「ネット対戦がおかしい」ときに最初に知りたいのは
「予測が原因か、それ以外か」で、`--net-no-rollback` はその問いに 1 コマンドで答える。
検証側 (`net_verify.bat` ケース D) にも同じ口を置いてある。

### なぜ「予測 tick を .rep に書かない」が中心的な設計判断か

書いてしまうと、巻き戻して走り直した tick が二重に並んだ .rep になり、
**このマイルストーン唯一の機械検証が成立しなくなる**。確定した tick だけを書けば、
ロールバック有りで録った .rep はロックステップのものと**バイト一致する**。
`net_verify.bat` はそれを「2 台の .rep 一致」+「ローカル 2P 参照とも一致」の
2 段で毎回確かめている — ケース C (遅延 1 / ロス 30%) は 21 回巻き戻しても一致した。

「ロールバックが sim を汚していないこと」を直接証明する手段は他に無い。ハッシュを
毎 tick 比べるだけでは「両者が対称に間違えた」場合を見逃す (M52h 申し送り 1 と同型)。

### なぜ desync 検出を「8 tick 刻みの checkpoint」にしたか

最初は「相手が最後に主張した (tick, hash) を毎フレーム比べる」で実装した。これは
**比較対象の tick が到着タイミングで決まる**ため、実測で片方が tick 60、もう片方が
tick 68 を desync として報告した。2 台のバンドルのフォルダ名が食い違うと、診断の
第一歩 (`--rep-diff` に 2 本を渡す) にすら進めない。刻みを固定すると、どちらも
「最初に食い違った checkpoint」という同じ答えに落ち着く。

厳密な初発 tick は checkpoint より前かもしれないが、それは `--rep-diff` が 1 行で出す
(実測: poke した tick 60 をそのまま名指しした)。**検出は粗くてよく、診断が細ければよい。**

### なぜ機種依存の値をスクリプトへ見せるのか (禁止しないのか)

「自分がどちら側か」を知らずに対戦ゲームの UI は書けない。一方でその値を sim 状態へ
入れれば必ず割れる。ここでエンジンが取れる立場は 3 つあった:

1. 見せない → UI が書けない。ネットコードとして使い物にならない
2. 見せて、書き込みを型で防ぐ → sim 状態かどうかは代入先で決まるので型では防げない
3. 見せて、**壊れたことを必ず検出する** ← 採用

3 が成立するのは desync 検出があるからで、この 2 つは**セットで 1 つの設計**。
`--net-demo` の `NetHudDemo` (UIElement = NoHash にしか書かない) と `NetDuelDemo`
(レーン入力 = 決定論の内側) が、使い分けの実例として同梱してある。

## 代替案

- **状態同期 (サーバ権威)**: 決定論を要求しない代わりに、帯域とサーバが要る。
  このエンジンは「Debug/Release/CI がビット一致する」を既に払い終えているので、
  その資産を使わない選択は高くつく。
- **予測なしの入力遅延増加**: 実装は最小だが、遅延が操作感に直結する。
- **スナップショットを毎 tick 全部保持**: 実装は単純だが 148KB × N が積む。
  確定フロンティアから先の 8 枚だけで足りる (リングは 12 枚)。

## 結果

- `.rep` / SimSnapshot blob の版 bump は**ゼロ**。増えたのはネットのプロトコル版
  (v1 → v2、ヘッダ +16 バイト) と ABI (v12 → v13、7 スロット) だけ。
- tick 末のワールドハッシュは**1 回に畳んだ** (クラッシュリング / タイムトラベル /
  ロールバックが同じ 1 個を使う。M52f 申し送り 6 の回収)。
- タイムトラベル (M52e) はネット中は起こさない。相手の居る tick 列を勝手に巻き戻しても
  相手はついてこないので、スクラブは原理的に成立しない。

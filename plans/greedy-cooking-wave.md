# M59〜M62: 超リアル物理 — 全体ロードマップ + M59 詳細計画

## Context

ユーザーの要求は「超リアルな物理演算を追加できるようにしたい」。対話で確定した中身は:
古典力学の修正 (空気抵抗・終端速度・マグヌス・ジャイロ項・浮力・風)、面ベース空力 (揚力・
失速・風見安定・翼面)、材料特性 (剛性・弾性・塑性・粘弾性・クリープ・応力緩和・強度・靭性・
脆性・延性・展性…)、関節・ラグドール・車両、XPBD 変形体、破壊、熱、流体、光学、電気導通。
**全機能は Inspector とスクリプトで ON/OFF・付け外し可能** (コンポーネント粒度 + bool
フィールド粒度の二段)。

### ユーザー決定 (確定)
1. **決定論は絶対維持** — 外部物理エンジン (Jolt/PhysX) は不採用。Jolt の決定論保証は
   同一バイナリ限定で、Debug/Release/WARP のビット一致という本リポジトリ最大の制約を満たせない。
2. 計画粒度 = **全体ロードマップ + M59 のみサブ詳細**。後続は着手時に詰め直す。
3. M59 の入口 = **空力・終端速度** (opt-in でビット互換維持)。ソルバ改装は M59 後半。
4. 材料 = **.physmat.json 資産 + コンポーネント側の個別上書き** (Unity 流二段構え)。
5. 熱・流体・光学・電気まで**全部ロードマップに含める** (粒子流体は実証スパイクのゲート付き)。

### M59k の申し送り (計画外の事実・罠)

1. ★**スクリプトから呼ぶ `AddComponentByName` は tick 末送りなので、直後の
   `HasComponentByName` は 0 を返す。** 計画は Remove 側の遅延しか意識していなかったが、
   スクリプト層は**アーキタイプのイテレーション中**に走るので Add も同じ経路 (ADR-005 の
   コマンドバッファ) に乗る。Has が答えるのは常に「この tick の頭の状態」。
   C# プローブの実走で初めて分かった (C++ の selftest はイテレーション外で叩いていて
   即時適用に見えていた) ので、PartSelfTest に `ForEachArchetype` の中から叩く試験を足して
   両方の挙動を固定した。EngineAPI.h / ScriptAPI.h / MyeScript.cs / engine_spec に明記。
2. ★**`GetContactInfo` は「今 tick の物理が書いた列」しか読ませない設計にした** (計画は
   「拡張 SolidContact を返す」としか言っていない)。接触列は毎 tick 使い回すバッファで
   **SimSnapshot 非被覆**なので、フェーズ 3 の Update から前 tick の列が読める状態にすると
   タイムトラベル復元 / ネットのロールバック後の再シムで割れる。
   実装は `TickRunner` が tick 頭で `SetTickContacts(nullptr)`、物理 Update の直後に
   実体を繋ぐ。**tick 番号の比較にしなかったのは意図的** — 「巻き戻し先の tick 番号が
   たまたま最後に物理を回した tick と一致する」経路 (投機 tick T を回した直後に T へ
   ロールバック) が理論上あり、ポインタの有無なら構造的に起こり得ない。
   結果として実データが返るのは **LateUpdate と OnCollision\* だけ**。
3. **計画の 8 本はそのまま採用。ただし `GetContactInfo` はペア引き 1 本**にした
   (列挙 API 2 本ではなく)。OnCollisionEnter(other) の形にそのまま噛み合い、
   既存の key 昇順二分探索をそのまま使える。列挙が要るのは M61 の破壊入力からで、
   そちらは C++ 側で `SolidContact` を直接舐めればよい。
4. **`SampleTerrainHeight` は「真下レイ」で実装した** (ローカル XZ の直接引きではない)。
   ハイトフィールドの逆変換は回転した地形で定義できない (鉛直線が局所で鉛直にならない) が、
   AABB の天井から真下へ既存のセル DDA を撃つ形なら回転・スケールに正しく、
   **描画ではなく当たる地形**を返す点も自動的に保証される。天井の 1m 上から撃つのは、
   ぴったり天井から始めると最高点の頂点をかすめるレイが誤差で外れるため。
5. **`World::IsBaseComponent` を公開した** (新規 1 関数)。基本 4 コンポーネントの
   remove は `RemoveComponentImmediate` が WARN を出して黙って無視する仕様だったので、
   そのまま委譲すると ABI が「1 (外した) を返したのに残っている」と嘘をつく。
   拒否判定を呼び側から見えるようにして戻り値を正直にした。
6. **計画外の追補: C# の `AddComponent` 糖衣が無かった。** `Engine.AddComponent` は v2 から
   internal で存在したのに `MyeScript` へ露出しておらず、**付けられるのに外せない/
   確かめられない**状態だった。v14 で 3 本そろえて `MyeScript` (self) と `MyeEntity` (他者)
   の両方へ出した。`GetContactInfo` / `AddForceAtPosition` / `WakeRigidbody` / `IsSleeping`
   も `MyeEntity` 側に生やしてある。
7. **実測 (Debug と Release でビット一致)**: 静止した m=1 の箱の法線インパルス
   = 0.16350 (= m·g·dt)、着地の瞬間 = 7.03049。端 (r=0.5) を押した箱の
   Δωy = -5.00000 (解析値どおり)。地形 (256x256, heightBase=-4/scale=36) の
   x=1000,z=0 で h=7.032。
8. C# 一時プローブは `assets\scripts\AbiProbe.cs` + scratchpad のシーン JSON で回した
   (`Runtime.exe --scene ... --frames 200 --warp --no-audio`)。**Release の
   MyeScripting.dll を焼き直し忘れると、プローブだけが古い DLL に対してコンパイルされて
   CS0103 で落ちる** — replay_verify のログにだけ ERROR が出て本体は PASS するので
   気づきにくい。ABI を触ったら両構成の build_managed を必ず先に回すこと。

### M59a2 の申し送り (計画外の事実・罠)

1. **`[phys] hash @240` はフィールド追加で必ず変わる** (ワールドハッシュに新フィールドの
   バイトが載るため)。a1〜e のビット同一証明の実手順は二本立て:
   ①`[phys] body` の pos/vel ビットパターン行 (挙動のみを表す — a1 がこの目的で追加済み) を
   変更前後で照合、②**2 段階ビルド** (フィールド追加のみ → 消費配線後) で hash @240 同士が
   一致すること (= 配線が既存シーンの 1 バイトも変えていない証明)。M59a2 で両方成立を実測。
2. 検証 (i) の等価並走も同じ理由で**ワールドハッシュ比較は原理的に不能** (physMaterial の
   AssetID 値自体が両シーンで異なる) → 剛体軌跡 (pos/rot/vel/angVel) の per-tick ビット比較で
   実装 (PhysicsSelfTest の dumpBodies)。
3. **質量は `EffectiveMassWorld` に一元化** — ソルバ収集だけでなく ABI の
   AddForce/AddImpulse/AddTorque も同関数を通す (計画の字面はソルバのみだが、質量が
   二義になると script の力積とソルバの応答が食い違う)。スケールは LocalTransform 直読み
   (ApplyTorqueWorld の慣性導出と同じ割り切り — スケール付きの親を持つ剛体では
   ソルバの親合成スケールと不一致。既存の慣性と同じ既知の限界)。
4. useDensity のフォールバック規約: 材料なし / コライダーなし / mesh (shape=3) / 体積 0 は
   従来式 `(mass>0)?mass:1`。トリガーコライダーの形状は質量導出に**使う** (形状と
   ソリッド性は独立。摩擦/反発の消費はソリッド時のみ)。
5. 実測: 静的床バウンド apex 1.369 vs 理論 h·e²=1.28 (離散 tick 分やや高め。窓 [0.9,1.5])。

### M59b の申し送り (計画外の事実・罠)

1. **a1/a2 と違い「二段階ビルド」も body ビット照合も要らなかった** — 新規は
   *フィールド追加* ではなく *コンポーネント追加* なので、既存エンティティは 1 つも
   新フィールドを持たない = `[phys] ... hash @240` 4 本と `[phys] body` 3 行が
   **変更前後で完全一致**する。これが M59b のビット同一証明そのもの (実測で一致)。
   Debug/Release も新ログ込みで全行ビット一致。
2. **基準面積は Cauchy の平均投影面積 (表面積 / 4) を採用** (計画は「投影面積スケール」と
   しか言っていなかった)。球で pi r^2、1 辺 a の立方体で 1.5 a^2 という既知値に一致し、
   「向きに依らない代表面積」を恣意的な平均でなく物理で決められる唯一の選び方。
   col なし / 動的 mesh は慣性導出 (LocalInertiaDiag) と同じ「半径 0.5 の球」既定へ落とす
   (0 を返すと空力が黙って効かなくなる)。
3. **角抗力のスカラー慣性は invI の対角平均**。ワールド逆慣性テンソルは既に組んであるので
   trace/3 を取るだけで済み、freezeRotation / kinematic が零行列 = 自動的に無効になる
   (別途の分岐が要らない)。
4. **マグヌス単独では速度ベクトルが等速で回り続ける** (力が常に v と直交する円運動、
   角速度 S*omega/m)。「N tick 後に vz が負」という素朴な断言は 1 周して落ちる —
   4 分の 1 周未満で*位置*の曲がりを見ること。陽的積分ぶん速さが 1 tick あたり
   約 0.3% 増えるのも同じ性質 (実運用では抗力・角抗力が吸収する)。
5. **落下する球にマグヌスは効かない** — 自由落下は omega // v になり外積が恒等 0。
   「空力が効いた」証明のテストには必ず水平初速を与える (最初に踏んだ罠)。
6. ★**セルフテストの罠: `AddComponent` の後にコンポーネントポインタを取り直す**。
   AddComponent はアーキタイプを移すので、それ以前に取った参照は tick 結果が反映されない
   古い記憶域を指す。**書き込みは生き残るが読み出しが古い**ので、
   「値を設定 → シム → 読む」を 1 本のポインタで書くとテストが**静かに空振りする**
   (4 項目が偽 PASS/FAIL になった)。既存テストが必ず ApplyStructuralChanges の後に
   GetComponent しているのはこのため。
7. 計画の「AeroComponent も存在ゲート 1 段」を **bool OFF は項ごとスキップ**まで詰めた:
   全項目 OFF の Aero は付けてもビット中立になる (風との相対速度への往復
   `v - w + w` すら走らせない — float では元の v に戻る保証が無いため)。selftest で固定。

### M59b2 の申し送り (計画外の事実・罠)

1. **v1 に復原モーメントは無い** (計画は「高さ比近似」としか言っていなかったが、その帰結)。
   AABB の高さ比では没水重心の**水平**ずれが出ないため、傾いて浮かぶ箱は傾いたまま。
   ただし力の適用は `ApplyImpulse(b, 0, 浮力中心-中心, 0, ...)` の形にしてあるので、
   M59f1 の質量中心オフセットが入れば r が水平成分を持ち、式を変えずに効き出す。
   本物の復原モーメント (面ごとの圧力積分) は M59c の仕事。selftest で「ω が厳密 0 のまま」
   を固定して制限を可視化した。
2. **球冠は多項式だけで閉じる** — V = pi(R^2 t - t^3/3 + 2R^3/3) /
   M = pi(R^2 t^2/2 - t^4/4 - R^4/4) (t = 水面Y - 中心Y)。逆三角関数を一切通さないので
   決定論の観点で最も安全。割合を返す形にすると pi が約分で消えて更に安い。
   半没の重心が 3R/8 下に来ることを解析値で固定。
3. **水中抗力を没水割合で按分すると、浅く浮く軽い物体はほとんど減衰しない** (実測:
   既定 drag=2 / 没水 5% で減衰比 0.004 = 30 秒経っても揺れ続ける)。物理として正しいので
   コードは直さず、平衡位置を測る試験側が drag を上げる。**計画の「浮上・沈降の定性」を
   位置で測るなら必ずこれを踏む**。
4. 浮力は陽的な復元力。安定条件は `rho_w * A_waterline * g * dt^2 / m < 4` (SpringJoint と
   同じ形)。既定の水と常識的な密度では 2 桁の余裕があるが、防波堤として
   `kExplicitMaxDeltaV` (マグヌスと共有、100 m/s) のクランプを掛けてある。
5. 水面は軸平行な Y 平面なので、**浮力の向きは +Y 固定** (大きさだけ |g| に従う)。
   重力を傾けたときに浮力だけ傾けても意味を成さない。
6. 実測: 密度が水の半分の球の平衡位置は **y = 0.0000** (中心が水面、解析値どおり)。
   密度 50 の球は **y = 0.365** (球冠の式 0.25t - t^3/3 = -0.075 の解と一致)。

### M59e の申し送り (計画外の事実・罠)

1. ★**法線インパルスは反復をまたいで積まないと意味を成さない** (計画は「法線インパルス
   合計」としか書いていなかった)。静止接触は 1 回目の反復でほぼ解決してしまうので、
   最終反復ぶんだけを記録すると**ほぼ 0** になり「載っている重さ」を表さない。
   8 反復の総和にすると質量 m の静止物でちょうど `m*g*dt` になる (実測 0.32700 / m=2)。
   M59g1 で蓄積インパルスへ改装しても意味は変わらないので、消費者 (M59k の接触 ABI /
   M61 の応力入力 / 衝撃音) は式を書き換えなくてよい。
2. 記録の位置を「マニフォールド生成直後」から「インパルスを出し終えた後」へ移した。
   push_back の順序は i<j x index 昇順走査のままなので **key 昇順は保たれる**
   (CollisionSystem の二分探索 FindContactNormal の前提)。ソルバ内側ループを
   range-for から index ループへ変えたが `[phys] hash @240` は全 4 本とも不変 (実測)。
3. 可視化のトグルを**プロセス全体のグローバル**に置けるのは、収集が read-only で
   出力が debugLines への一方通行だから (selftest が「収集あり ⇔ 収集なし」の
   並走ハッシュ一致と「線を組んでもワールドハッシュ不変」の 2 本で固定)。
4. 呼び出しは **TransformSystem の後** (速度ベクトルの根元に当 tick のワールド行列が要る。
   接触点は SolidContact 自身がワールド座標を持つのでどちらでもよい)。
   **再シム中は抑止**する — 巻き戻すたびに積み直すとシークの途中経過が 1 フレームに
   折り重なって見える。
5. 出力先が debugLines なので **GameView にも出る** (スクリプトの DebugDrawLine と同じ
   レーンに相乗り)。逆に**編集中 (非 Play) は 1 本も出ない** — 積むのは tick 側なので。
   SceneView のボタンは有効中に着色して「押したのに出ない」と迷わせないようにした。

### M59c の申し送り (計画外の事実・罠)

1. ★★**対称な凸形状に一様流を当てても、幾何中心まわりのトルクは原理的に厳密 0**。
   平らな面にかかる圧力は一様なので合力は必ず面心を通り、面心は法線軸上にある
   (r // n // F → 外積 0)。**面の分割数を上げても変わらない** (同じ面の小片は同じ法線・
   同じ un を持つため)。計画の「風見安定は面積分の別成分として自然に出る」は、
   正確には「**圧力中心が質量中心からずれていれば**自然に出る」。本エンジンでは
   M59d の翼面 (子エンティティ = 親の中心からずれる) と M59f1 の質量中心オフセットが
   その役を担う。selftest は 0 であることと機構 (尾翼は復元 / 前翼は不安定化・レバー比に線形)
   の両方を固定した。**M59d の設計はこの事実の上に立つ**。
2. 係数の対応を `Cn = Cd/2` に固定した — 正対した平板の抗力が教科書の 1/2 rho Cd A u^2 と
   一致する唯一の取り方。同じ Cn で球を面積分すると実効 Cd は Cn (= 平板の半分) になるが、
   これは Newton 流モデルの答えそのもので実測比 (0.47 / 1.28 = 0.37) とも整合する。
   細分割した球 (128x256) が解析 1 発と **0.001% で一致**することを実測 (23.1000 vs 23.1003)。
3. **カプセル端の半球は「面積 pi R^2 / 2 の円盤」に置き換えられる** — 軸方向の流れに対する
   半球の圧力積分がちょうどこの円盤と一致する。halfSeg=0 のカプセルが解析球と一致することで
   機械照合できる (傾いた流れでの横力は落ちる既知の近似)。
4. 方位分割は**定数表**で持つ (std::cos/std::sin は CRT 実装依存でビットが動きうる)。
   8 分割なら値は 0 / ±1 / ±sqrt(2)/2 の 3 種だけ。
5. AeroComponent は「抗力を出すか (enableDrag)」と「どう出すか (surfaceModel)」の 2 段。
   マグヌスは常に等方経路のまま (面モデルは向きを見る抗力だけを受け持つ)。
6. 実測: 質量 0.2kg・1.2m 角の板を +Z へ 8m/s で射出 → 面モデル z=8.58 y=12.25 /
   等方近似 z=1.76 y=9.22 (面モデルの方がよく滑空する = 向きを見ている証拠)。

### M59d の申し送り (計画外の事実・罠)

1. ★**失速後の CL は「平板値へ落とす」であって「平板値を失速点で連続になるよう正規化する」
   ではない**。2 sin cos は 45 度で最大なので、正規化すると失速後に CL が CLmax の
   2 倍まで**増えて**しまい失速の意味が逆転する (最初にこれを書いて試験で捕まえた)。
   素の平板値は失速点で CLmax より低いので、そこへ向かって落とすのが揚力の崩壊そのもの。
   段差でびびらないよう失速角の 0.5 倍幅で線形に混ぜてある。
   実測: 迎角 14.5 度で dvy 5.15 → 23.6 度で 2.51。
2. 迎角は角度そのものでなく **sin(alpha)** で持ち回る (揚力傾斜も dCL/d(sin alpha))。
   小角度では同値で、**逆三角関数を一度も呼ばずに済む**。
3. ★**揚力は前進成分を持つ**。流れに垂直なので、前下方から風を受けると揚力の向きが前へ傾く
   = 降下しながら前へ伸びる (滑空そのもの)。「翼を付けたら前進が遅くなるはず」は誤りで、
   正しい断言は「**揚力は仕事をしない = 速さは必ず減る**」(F.v = -q A CD |v| < 0)。
4. 力の入り先は「自分 → 祖先」で最初に見つかった動的剛体。孫でも届く (試験で固定)。
   走査順は entity.index 昇順。
5. ショーケースの .physmat は **名前で引く** (`FindPhysMat`)。絶対パスのハッシュを組むと
   チェックアウト先で変わるうえ、同伴 .meta の GUID が優先されるので一致しない
   (M59a1 の申し送り 1)。床は x=4 で切ってあり、その先が水面 = 浮きの居場所。
6. replay_verify は **5 ペア**になった (demo + parts + flow + mp + physics)。
   snapshot 往復ストレスも 5 本目を追加。所要は約 +80 秒。

### M59g1 の申し送り (計画外の事実・罠)

1. ★★**点毎 Jacobi の `1/count` 緩和が蓄積インパルスでは律速になる**。M28b は毎反復
   ゼロから解き直していたので緩和が正しかったが、蓄積すると 4 点マニフォールドで
   毎反復 1/4 しか進まず、8 反復では **2 段タワーすら静定しない** (下の接触インパルスが
   理論値 2*m*g*dt の 88%、上の箱が跳ね続ける)。緩和を外すと **0.32704 / 理論 0.32700**。
   蓄積 + 0 クランプがあれば緩和なしでも暴れない。**一括適用 (Jacobi) は維持**すること —
   点を順に適用すると走査順の非対称がトルクとして残り対称なスタックが歩き出す。
   ※最初これに気付かず反復回数を 8→16→24→32 と振ってしまった (全部対症療法)。
2. ★**位置補正は速度ソルバから分離しないと成立しない**。生成時に固定した接触点・法線・
   有効質量と、解いている最中に動く姿勢が食い違う。分離前は 2 段タワーが跳ね続け、
   下の接触インパルスが理論値の **2.3 倍**に膨らんだ。分離後は「速度ソルバ = 生成 1 回、
   位置補正 = 毎回 CollideManifold」に役割が割れて素直になる。計画は「溢れそうなら g2 へ

3. **位置補正パスは 8 回必要**。4 回に減らすと 10 段スタックが床を突き抜けて -975m まで

4. **tick あたりのコストはむしろ下がった**: M28b は反復ごとに CollideManifold (8 回)。
   いまは生成 1 回 + 位置補正 8 回で、速度反復は有効質量も作り直さない安い計算。
5. **計画が予告した「約 45 項目の再基準化」は不要だった** — 既存の全項目が窓のまま通った。
   `:315` の `==` 比較は freezeRotation の不変量 (姿勢ビットが動かないこと) であって
   チューニング値ではないので、窓比較へ書き換えては**いけない**。
6. **golden スクショ 12 枚は 1 枚も動かなかった** (parts.png 含む)。tick 3 の被写体が
   自由落下中で接触ソルバに触れないため。計画は g2 で parts.png 再記録を見込んでいたが、
   g1 では不要。
7. ★**M59h の計測ゲートの答えが出た** (1200 tick 後の最上段 y / 最大水平ドリフト):
   | | M28b | M59g1 |

### M59g2 の申し送り (計画外の事実・罠)

1. ★★**e=1 の反発で discrete ソルバは頂点を「失う」のではなく「増やす」**。実測の回復率は
   substeps 1 = **108.1%** / 4 = 102.7% / 16 = 100.6%。反発バイアスは生成時の接近速度で
   1 回だけ決まる (M59g1) が、接触を検出した時点でその速度には**重力 1 ステップぶんの
   余剰**が乗っている。だから跳ね返しすぎる。計画の「頂点保存 ~99%」は下から近づく前提
   だったが**上から近づく** — 判定は「100% からの乖離が単調に縮む」で書くこと
   (最初 `r4 > r1` と書いて落とした)。
2. ★**静的コライダーは既存フィールドとしての反発係数を持たない** (M59a2 の仕様)。
   `e = min(ea, eb)` なので、球に e=1 を与えても素の床は 0 のままで**一度も跳ねない**。
   反発を測る試験には `.physmat` を 1 枚仕込む必要がある (最初これで頂点が測れず
   回復率 -33% を出した)。engine_spec 10.3 の「材料付き静的コライダーの e 主張」が
   ここで初めて必須機能として効いた。
3. ★**減衰はサブステップごとに掛けてはいけない** — `linearDamping`/`angularDamping` は
   「毎 tick の率」と仕様に書いてある。h ごとに掛けると (1-d)^N になり、substeps を
   上げただけで減衰が強くなる。最初のサブステップで 1 回だけ適用する。
4. ★**接触インパルスはサブステップをまたいで「足す」**。平均を取ると substeps を上げる
   だけで報告値が 1/N になり、「この tick に入った法線インパルス」という意味が壊れる
   (静止体は substeps に依らず m*g*dt であるべき — 実測 1/4/16 すべて 0.16350)。
   `MergeSubstepContacts` が key 昇順の線形マージでこれをやる (幾何は後の substep を採る)。
5. **反発の速度閾値も h に合わせて縮める**。`kRestitutionVelThreshold` は「重力が 1 ステップで
   与える速度の ~2 倍」という設計なので、固定のままだと**サブステップを増やすほど
   跳ねなくなる**という逆転が起きる。
6. ★★**M59h のゲートの答えが変わった** — M59g1 で「1cm ジグザグ 10 段は崩れる →
   warm starting が要る」と結論したが、**substeps=8 なら立つ** (@1200 tick で頂点 9.483 /
   ドリフト 0.73。built は 9.5)。1 と 4 では崩れる。整列 10 段も 9.416 → 9.494 と
   貫通の蓄積が減る。**warm starting はコストのための答えであって唯一の答えではない**
   — M59h では「warm starting 有り substeps=1」と「無し substeps=8」を並べて測ること。
7. **剛いバネの安定限界は substeps で買える** (計画どおり)。k=20000/m=1 (omega=141) は
   60Hz で h*omega=2.36 = 発散側。実測の最大伸びは substeps 1 で **30.6m**、4 で **0.105m**
   (初期変位 0.1m)。SpringJoint の Δv クランプ 100m/s は**サブステップごと**に効くので、
   実効上限は 100*substeps m/s へ緩む (発散防止の防波堤としては十分)。
8. **崩れた塔の評価には広い床が要る**。M59g1 のゲートは 6m 床で、substeps=4 のとき箱が
   水平 93m まで飛んで**端から落ち**、y=-788m になった。「床を抜けた」と区別が付かない
   ので M59g2 の塔試験だけ床を 60m にしてある (数字を g1 のゲートと直接比べないこと)。
9. **substeps=1 は M59g1 と同じ経路**だが、**env を置いた時点で既定 4 が効く**。
   PhysicsEnvironment は「値の出所」から「**積分スケジュールの選択**」へ意味が広がった —
   env の有無が違う 2 シーンは Buoyancy も Aero も持たないボディの軌跡まで割れる
   (浮力の混在試験がこれで落ち、参照側にも同じ env を置いて直した)。

### M59f1 の申し送り (計画外の事実・罠)

1. ★★**後退 Euler ではなく陰的中点にした**。計画は「implicit」としか書いていないが、
   後退 Euler (Bullet の実装) は保存則を 1 つも持たず、無トルクの箱の |L| が実測で
   **4 秒に 7.3% / 15 秒に 23%** 落ちた。陰的中点はこの系の二次不変量を保つので
   同条件で **15 秒に 0.006%**。**1 反復目は ω̄=ω₀ で後退 Euler と同一式**なので、
   `kGyroIterations` は 2 以上でないと中点にならない (現在 3)。
   シンプレクティックな解法はエネルギーが**振動する** = 「単調非増加」を断言しては
   いけない (「有界」で書く)。計画の「|ω| 非増加」も誤り — |ω| は自由回転で保存量では
   ない (保存するのは |L| と T)。
2. ★**テニスラケット定理の観測量はボディ座標系の ω₂**。ワールドの ω_y を見ても反転
   しない (無トルクなら L はワールドで不動なので、ワールド ω はほとんど符号を変えない)。
   最初これで「効いていない」と誤診した。
3. **球にはジャイロ項が効かないのが構造から言える** — J の非対角は行 i が共通因子
   (I_{i+2} − I_{i+1}) を持つので、主軸慣性が等しければ J は対角で f も恒等 0。
   特別扱いの分岐は要らない (実測ドリフトは 240 tick で 1e-5 rad/s = 丸めだけ)。
4. ★**COM は「値ゲート」ではなく「分岐ゲート」**にした。`p + 0.0f` は -0.0f を +0.0f に
   化けさせるので「0 を足しても同じ」に依存できない (決定台帳 1 と同じ)。**ただし
   引き算は別** — `x - (+0.0f) == x` は -0.0f も含めて成立するので、腕の計算
   (`p - pose.p - com`) は com を +0.0f 固定にしておけば無条件に書ける。
   位置積分だけは足し算になるので `if (hasCom)` で経路を分けてある。
5. **慣性テンソルは平行軸で移し替えない** — 形状から導いた対角慣性を**宣言された
   質量中心まわり**として扱う (Unity / PhysX 規約)。重心をずらす = 質量分布が形状と
   違うという宣言なので、移し替えには根拠が無い。
6. ★**接触の腕の効果は箱では見えない**。4 点マニフォールドの点毎 Jacobi が不均衡を
   打ち消すので、重心をずらした箱が着地しても正味の回転は 0.0168 (符号も直感と逆)。
   **球なら接触点が 1 つ**で τ = r × j がそのまま出る (実測 ω_z = ∓5.51)。
   腕そのものの試験には 1 点接触の被写体を使うこと。
7. **M59b2 / M59c の予告を回収した**: 重心を下げた浮体は 20 度の傾きが 0 まで戻る
   (重心が形状中心のままだと傾きが**厳密に**保存される = 予告どおり)。面サンプリング
   空力も重心をずらすと前後で等大逆符号のモーメントが立つ。
   面カーネルへは `v − ω×com` を渡し、返ってきたトルクを `τ − com×F` で移す。
8. **等方抗力・マグヌス・ConstantForce・SpringJoint・重力は質量中心に効く**まま
   (モーメントを作らない)。等方モデルには圧力中心の概念が無いので、ここで腕を
   持たせるのは意味を成さない — それをやるのが面モデル (M59c) の役割。
9. **ビット中立の証明は 2 段階ビルド** (a2 の申し送りの手順)。フィールドだけ足した
   ビルドと配線後のビルドで `[phys]` ログ 32 行 (4 つのシーンハッシュ込み) が完全一致。
   ハッシュ自体はフィールド追加で必ず変わるので、`[phys] hash @240` の値そのものを
   前コミットと比べても意味が無い。
10. **ショーケースに 2 体足した** (`--physics-demo`): 重心を下げた Buoy (自己復原) と
    中間軸で回る Tumbler (gyroscopic=true)。新しい経路を replay_verify の
    Debug/Release ビット照合に載せるため。

### M59f2 の申し送り (計画外の事実・罠)

1. ★**ビット同一の根拠は「材料が無ければ μs は μd と同じ既存フィールドを返す」**こと。
   ペア係数が `sqrt(μsa·μsb)` と `sqrt(μda·μdb)` で**同じ式・同じ入力**になるので
   ビットまで一致し、静止/動の分岐が従来の 1 本のクランプへ畳まれる。
   実測でも既存の [phys] ログ 32 行が 1 ビットも動かなかった。
2. ★**転がり抵抗だけ結合則を max にした** (摩擦の sqrt(積) ではない)。転がり抵抗は
   どちらか一方の材料のヒステリシスで生まれるので、sqrt(積) だと「素の床に置いた
   ゴム球が永久に転がる」という**間違ったほうの既定**になる。1 体にだけ設定される
   ことが最も多いプロパティなので、ここは対称性より実用を採った。
3. **摩擦の override ビットは μs と μd をまとめて覆う**。Collider 側の格納庫が
   `friction` 1 本しかない以上、片方だけ既存フィールドへ戻す意味が無い。
   転がり抵抗には既存フィールドが無いので、新ビット `kPhysMatOverrideRolling` (1<<2) は
   「0 を使う」を意味する。
4. **転がり抵抗は純粋な角インパルス**で、並進には一切足さない。ω が枯れる → 滑りが
   出る → 摩擦が v を落とす、という接触経由の連鎖で止まる。上限は Crr·ΣJn·R
   (R = 接触点までの腕の長い側)。実測: 3 m/s で放った球が Crr=0.05 で **v も ω も
   厳密に 0** になる (Crr=0 なら 900 tick 後も 2.14 m/s)。**M59h のスリープが
   要求する「本当に静止する」はこの段が作る**。
5. **転がり軸も生成時に固定する** (摩擦の接線と同じ理由)。蓄積インパルスは回る軸を
   追いかけられない。回っていない接触は軸が定義できないので無効化する。
6. 実測のヒステリシス (θ=26.565 度 / tanθ=0.5 / μs=0.9 / μd=0.2、60 tick):
   動摩擦だけ (0.2) なら **-1.19m 滑る** / 材料付きで静止からは **-0.0018m** /
   1 m/s 押すと **-2.09m 滑り続ける**。計画の要求どおりの 3 点が出た。
7. **プリセット 4 種 (a1 で作成済) は既に μs≠μd と Crr を持っている**ので、
   `--physics-demo` は何も足さずに新しい経路を replay 被覆に載せる
   (Crate が steel/rubber、床が steel)。

### M59h の申し送り (計画外の事実・罠)

1. ★★**warm starting は入れなかった** (予約事項 1 の箱は開けない)。g1 のゲートは
   「1cm ジグザグ 10 段が崩れる」だったが、g2 で **substeps=8 なら立つ**ことが分かった
   ため、計画の延期条件をそのまま満たしている。M60 で必要になったら別コミットで。
2. ★**閾値の置き場を PhysicsEnvironment にした** (計画は置き場を書いていなかった)。
   スリープを既定 on にすると既存シーンの挙動が全部変わるので、存在ゲートの内側に
   入れるのが M59 の一貫した答え。実測でも 2 段階ビルドで **env の無いシーンは
   4 つのハッシュを含めて 1 ビットも動かなかった** (動いたのは浮力の 2 行 = env を
   持つシーンで浮体が眠るようになったぶんだけ)。
3. ★**眠っているペアは「解かないが報告する」に変えた** (計画は CollisionSystem 側に
   「両者睡眠なら前 tick から Stay を繰り越す」規則を足す案)。PhysicsSystem 側で
   最後のサブステップにマニフォールドを 1 回作り、**インパルス 0** で報告する。
   利点は (a) エンティティの生存確認が要らない (b) 毎 tick 実際に重なりを確かめるので
   記憶から嘘をつかない。CollisionSystem は 1 行も触っていない。
   ★**副作用**: 眠っている接触の報告インパルスは 0 になる。M59g2 の
   「静止インパルス = m*g*dt」試験はこれで落ちたので、その試験では
   `sleepDelayTicks = 0` にしてスリープを切ってある。
4. ★**sleepTicks を閾値でクランプする**のが「眠っているあいだハッシュが動かない」の
   要。クランプしないと眠る前も眠った後もカウンタが毎 tick 増えてハッシュが揺れる。
5. **不動化は invMass = 0 + freezeRot で行う** — 各帯に `if (sleeping)` を撒かずに、
   既存の `invMass == 0` 分岐へ自然に落とす。ブロードフェーズには残す
   (外すと起きているボディがすり抜ける)。起こすときに戻す値を Body に控えておく。
6. **床は起床トリガにならない** (判定が `invMass > 0` = 覚醒中の動的剛体のみ)。
   これが無いと床の上で寝ているボディが毎 tick 起こされる。
7. **島は静的/kinematic を繋がない** — 繋ぐと床を介して世界中が 1 つの島になり、
   どこかで 1 体でも動いていると誰も眠れなくなる。根は最小 index へ正規化
   (ペアの処理順に依らずラベルが一意)。
8. **計画の「アイランドラベルを総当たり⇔sweep で照合」は実装しなかった** — union-find は
   ソルバ内部の一時データで外から観測できない。代わりに**振る舞い**で断言している
   (3 段の塔が**同じ tick に揃って眠る** / 別々の塔は独立に眠る)。観測点を足すために
   API を広げるより、意味のある不変量を試験するほうが良いと判断した。
9. **ABI の起床配線は既存 4 スロット** (AddForce / AddImpulse / AddTorque / SetVelocity)。
   `WakeRigidbody` / `IsSleeping` そのものは計画どおり M59k で足す。
10. 実測: 静止した箱は閾値 60 tick に対し **tick 59** で入眠 (着地から数えて)、
    以後 120 tick ワールドハッシュがビット同一。3 段の塔は **59/59/59** で揃う。
11. ★試験を書くときの罠 (再発): **同じアーキタイプにエンティティを足すと列が再確保され、
    先に取ったコンポーネントポインタが死ぬ**。投擲物の試験で「箱は動いたのに
    isSleeping が false にならない」が出た。ポインタは**最後の構造変更のあと**に取る。
12. ★起床は **AABB + margin の近接**で起きるので、覚醒した瞬間はまだ触れていない。
    「起きたら即動いている」を断言すると落ちる (数 tick 待つこと)。

### M59i の申し送り (計画外の事実・罠)

1. ★★**地形データを sim 用に別で持つ**ことにした (計画は「TerrainData 注入は meshcol::
   流儀」としか書いていなかった)。描画側 TerrainSystem のキャッシュを読むと
   **「絵を出したかどうか」で sim が変わる** — ヘッドレス selftest / `--warp` /
   replay / 最小化ウィンドウで結果が揃わなくなる。メッシュコライダーが
   RenderResources の CPU 頂点を借りているのとは事情が違う (あちらは「資産の中身」、
   地形は「描画システムの作業表」)。
2. **shape=3 と shape=4 を「三角形スープ」として一本化した**。差し替えたのは
   `SoupGatherTris` (候補の集め方) と `SoupWorldTri` (番号 → ワールド三角形) の 2 つだけで、
   衝突・マニフォールド・最近点の本体は M41 のまま。`meshData` は shape 値で判別する
   タグ付き共用体にした (ShapePose を太らせない)。
3. **BVH は要らない** — セル格子なので候補は AABB からの矩形走査で直接刻める。
   `tri = (iz*tilesX + ix)*2 + half` で、iz 外・ix 内に回せば三角形番号が自動的に昇順。
4. ★**レイキャストだけは AABB 一括収集にできない**。斜めに長いレイは矩形が地形の
   ほぼ全体になり、候補上限で**静かに取りこぼす** (メッシュは BVH があるので同じ形でも
   困らない)。XZ セルの DDA (Amanatides-Woo) で辿る。試験に「長い対角レイ」を 1 本
   入れてあるのはこの回帰を止めるため。
5. ★**HeightAtTexel を直接呼ばない** (計画どおりの罠、実装でも守った)。引数が uint32_t
   なので負値が 0xFFFFFFFF に化け、内部の std::min クランプで**反対側の端**に落ちる。
   右半分だけ 100m 高い地形の左端外側を撃つ試験でここを固定してある。
6. **頂点位置・巻き順は BuildChunkMesh (LOD 0) と同じ式**にすること。ずらすと
   「見えている地面」と「当たる地面」が別物になる。
7. **高さの範囲はロード時に 1 回だけ測る** (`TerrainCollisionData`)。ComputeAabb は
   ブロードフェーズで毎フレーム呼ばれるので、そこで W*H を走査してはいけない。
8. **CC は何も足さずに歩けた** — CC は Collide / DistanceToShape / ClosestPointOnShape を
   通して障害物を見ているので、その 3 つに shape=4 を足した時点で対応が済んでいる。
9. **未解決の地形は「衝突なし」に落ちる** (メッシュと同じ規約)。負のキャッシュを
   持たせて毎 tick のロード試行を止めてある。
10. ★試験の罠: **自由落下の期待値は半陰的 Euler の離散和** `g*dt²*n(n+1)/2` で書くこと。
    連続解 `0.5*g*t²` だと 60 tick で 0.0133 vs 0.0950 と全く合わない。
11. 実測: 高さ 3.0 の平坦地形で球が **2.9995** に静定 / 20m の斜面を **-12.6m** 転がる /
    放物線の谷で箱が底へ寄る / 真下レイが **t=19.9998** (真値 20) / CC が接地して
    5m 歩く。既存の [phys] ログ 41 行は 1 ビットも動いていない。
12. **計画の「play 中の地形編集は sim に反映されない契約」** はライブラリのキャッシュが
    そのまま体現している (M58f のブラシは描画側キャッシュだけを更新する)。
    明示的な無効化 API は付けていない — 必要になったら `TerrainColliderLibrary::Clear()`。

### M59j の申し送り (計画外の事実・罠)

1. ★★**TOI で止めるだけでは足りない — 法線インパルスを 1 発入れるのが設計の中心**。
   位置を詰めるだけだと速度が残り、次サブステップも同じしきい値を超えて同じ TOI で
   止められる。貫通が生まれないので接触も作られず、離散ソルバへ引き継げないまま
   **壁の手前で永久に浮く**。応答を入れると速度が落ちて起動しきい値を外れ、そこから先は
   通常のソルバ (摩擦・スタック・接触継続) が面倒を見る、という受け渡しが成立する。
2. ★★**「かすり」判定が要る**。掃引が当たっても、**法線方向の進みが小さいなら止めない**
   (`-vn*h <= kCcdMotionRatio*R` で降りる)。これが無いと、接している面に沿って高速で
   滑るボディが凍る — 面から 1mm 浮いて僅かに沈み込んでいるだけで掃引は「触れる」を
   返すので、TOI≈0 で**接線方向の移動量ごと**削られてしまう。貫通は法線方向の現象なので
   判定も法線方向の移動量で行う。selftest の「滑走が 100m 進む」がこの回帰。
3. ★**起動しきい値 (`|v*h| > 0.5*R`) は速度のためではなく正しさのため**にある。低速でも
   掃引すると 1 の浮きが常態化する。「速いあいだだけ CCD が持ち、止まったら離散へ返す」
   という受け渡しの契約そのものがこの値で決まっている。
4. **相手は掃引でも応答でも不動として扱う**。掃引が相手を止めて見ている以上、応答だけ
   2 体拘束にしても筋が通らない。CCD ボディ同士が正面衝突すると各自が自分を止めるので
   その 1 発では運動量保存が崩れるが、次サブステップからは通常ソルバが正しく解く。
5. **SphereCastWorld は呼べない** (計画の「既存実装を再利用」は*手法*の再利用と読むこと)。
   あちらは WorldMatrixComponent 基準で、TransformSystem がまだ走っていないこの時点では
   **1 tick 古い**。おまけにトリガーも拾い、スリープ/kinematic の区別も持たない。掃引の
   材料はソルバが握っている `bodies[]` の pose でなければならない。手法 (sphere/capsule は
   半径膨張レイの解析解、box/mesh/terrain は DistanceToShape の保守的前進 32 回) だけを写した。
6. **移動体は外接球で掃く**。box/capsule では真の掃引形状より大きいので TOI は手前に出る =
   「貫通しない」側へ倒れた保守的な誤差。実測: 半径 0.2 の箱 (外接球 0.346) は壁面 8.0 の
   手前 **7.603** で止まる (球の弾は 7.849 = 壁面 − 半径 − skin でほぼ厳密)。
7. **置き場は「位置補正の後・位置積分の前」**。このサブステップの最終ポーズが確定していて、
   まだ誰も前進していない唯一の地点。★位置積分ループの中で 1 体ずつやると、相手のポーズが
   「もう積分した/まだの」で混ざりボディの走査順が結果に載る。
8. 位置積分へは**係数ではなく移動量そのもの**を渡す (`Body::ccdDx/Dy/Dz`)。CCD は止めると
   同時にインパルスを入れるので、積分の時点の `b.v*` は掃引に使った速度と既に別物。
9. **CCD の接触も outContacts に載せた** (計画外)。反発で跳ね返る弾は貫通を作らないまま
   離れていくので、載せないと OnCollisionEnter が一度も飛ばない。key 昇順の契約があるので
   ソート + 同一 key の畳み込み (両側から報告されうる) を挟んでから MergeSubstepContacts。
10. ★**ショーケースの弾に鋼材料を付けてはいけない** (実測で踏んだ)。e=0.6 だと CCD の
    一発インパルスが 1.6 倍の跳ね返りを作り、弾が 72 m/s で後ろへ飛んで床の端を越え、
    以降 600 tick ずっと落下し続ける。材料なし (e=0) で壁に食い込んで止まるのが正解。
11. 実測: 200 m/s の球 (半径 0.1) は CCD 無しで厚さ 0.1m の壁を**確実に抜ける** (x=20.0)、
    CCD 有りで **7.849** に停止 + vx=0 + 接触報告あり。ショーケースの弾 (120 m/s) は
    壁面 **-8.131** で止まり床の y=0.0795 へ落ちて入眠。既存の `[phys]` ログ 47 行は
    1 ビットも動いていない (動いたのはワールドハッシュ 4 本 = `ccd` フィールド追加のぶんだけ)。
12. `--physics-demo` に CCD の被写体 (ThinWall + Bullet) を足したので、**replay_verify の
    5 ペア目が CCD 経路を Debug⇔Release で被覆する**。

### マイルストーンを跨ぐ予約事項 (今決めておかないと後で全部やり直しになるもの)

1. **ステートフルバックエンドの導入様式** — M59 では箱を開けない (スリープはコンポーネント
   常駐で実現)。M60' の XPBD 着手時に、WorldHasher の `const CpuParticleBackend*` 名指し
   シグネチャ (~60 呼び出し) を「sim 状態源の集約 struct」へ置換する**準備コミットを独立で
   切る**。以後のバックエンド追加は SimSnapshot 節 1 個の追加に縮む。
2. **SolidContact の拡張形** (M59e で確定) — 「ペアキー + 法線 + 代表接触点 + 法線インパルス
   合計」。消費者は可視化 (M59e)・接触 ABI (M59k)・破壊の応力入力 (M61)・衝撃音 (将来) の 4 者。
3. **面サンプリングカーネルの API** (M59c で確定) — 「表面要素 (点・法線・面積・その点の速度)
   → 力・トルク蓄積」の純関数。M60' の布が第 2 の呼び手になることを前提に署名を切る。

## M59 詳細 (16 サブ、1 サブ = 1 コミット = 1 セッション)

**列: a1 → a2 → b → b2 → e → c → d → g1 → g2 → f1 → f2 → h → i → j → k → l**

順序の根拠:
- 可視化 (e) を面空力 (c/d) より前に — 面ごとの力ベクトルが見える状態で開発する。
- **ソルバ改装 (g) を回転力学 (f) より前に** — f の静動摩擦分離・転がり抵抗はソルバループ
  本体に書くため、f 先行だと g で書き直しになる。サブステップ (g2) は実効 dt を変えるので
  dt 依存チューニング (ジャイロ・摩擦・kRestitutionVelThreshold「~2g·dt」) は g2 の後に 1 回で済ます。
- golden (physics.png) は挙動が固まる最後 (l) に 1 回だけ記録。
- a1〜e は既存シーンをビット同一に保つ (機械的証明つき)。**数値が動き始めるのは g1 から**。

### M59b: PhysicsEnvironment + 等方空力
- `PhysicsEnvironmentComponent` (TypeId 36): gravity (Float3 既定 0,-9.81,0) / airDensity
  (1.225) / windVelocity (Float3) / waterPlaneY / waterDensity。消費は Skybox/Fog と同じ
  「entity.index 最小の active な 1 個」規約。登録は消費者と同一コミット (未検証コンポーネント
  を漂わせない)。
- `AeroComponent` (TypeId 37): enableDrag / enableMagnus / enableAngularDrag (Bool 群) +
  Cd 上書き / 投影面積スケール / マグヌス係数。
- 実装は ConstantForce 帯の直後。等方二次抗力は**閉形式 implicit**: `v ← v/(1+(k·|v|/m)·dt)`
  (除算のみ、無条件安定)。風は相対速度 `v−v_wind` を抗力に食わせる。マグヌス `F = S(ω×v)`。
  **角速度二次抗力も入れる** (無いとマグヌスで回る球が永遠に回り続ける — angularDamping は
  非物理の定率なので置き換え候補として併存)。
- ★**fast-path は値ゲートでなく存在ゲート**: env コンポーネント不在 → 現行の
  `b.vy += kGravity * gravityScale * dt` (:507) を 1 文字も変えずに通す分岐。
  理由: -0.0f + 0.0f = +0.0f でビットが変わるため、gx=0 でも無条件ベクトル加算は不可。
  「env を置いた = 挙動変更に opt-in」が契約。AeroComponent も「装着 = 新数式に opt-in」の
  1 段で切る (係数 0 でのビット中立は約束しない)。bool OFF は項の計算ごとスキップ。
- **CharacterController は M59 では env に従わない** (kGravity 直参照 :261 + Y 軸前提の
  接地判定のまま) — 文書化して据え置き。任意重力ベクトルは CC の意味論を壊すため。
- 検証: 終端速度の閉形式一致 (v_t = √(mg/k))、風中の抗力平衡、マグヌスの曲がり方向 (符号断言)、
  Aero 非所持ボディ混在シーンで非所持側ビット不変 (並走ハッシュ)、fast-path ログ照合。

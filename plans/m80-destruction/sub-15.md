## やること

### A. 拡張点の確認 (5 件)。各件について「今の設計で将来の拡張がどこに入るか」を確かめる
既存のコードで足りていれば ADR-021 に書くだけにする。足りなければ、**挙動を変えない小さな構造変更** (関数の切り出し・資産形式の欄の確保) を入れる。

1. **破片ごとのスキン描画**
   - 確かめること: `.mfrac` の破片メッシュ (`MeshVertex`) が、骨 index とウェイトを持てる形になっているか (今は 0 で埋めている)。描画の分岐が `ShouldHideUnbrokenFracturePiece` の 1 か所に集まっているか
   - 将来の差し込み口を ADR に書く: ウェイトを `.mfrac` に残す、破片の MeshRenderer に SkinnedMesh の骨パレットを渡す
   - `.mfrac` の版を上げずにウェイトを入れられるなら、**今の焼きでウェイトを保存しておく** (描画はまだ使わない) かを検討し、判断を SELF_EVAL に書く
2. **接地アンカーの判定**
   - 確かめること: 「分離のとき、どの成分がルートに残るか」(今は体積最大) と「kinematic かどうか」の決定が、FractureSystem の中で**1 つの関数**になっているか
   - なっていなければ、挙動を変えずに切り出す (例: `SelectStayComponent`)。将来のアンカー判定は、その関数を差し替える形になることを ADR に書く
3. **凸分解**
   - 確かめること: `.mfrac` の破片レコードが凸包を 1 個しか持てない形か (`FractureAsset.h` の `PieceRecord::hull`)。`BuildFracturePieces` が破片エンティティに Collider を 1 つだけ付ける形か
   - **`.mfrac` の破片レコードを「凸包の個数 + 凸包の列」にする版上げ (v2、v1 も読める)** を今やるかを判断する。やるなら今の焼きは常に 1 個を書く (挙動不変)。やらないなら、将来の版上げの手順を ADR に書く。判断の基準: 今やる費用 (読み書きとテスト) と、後で既存の `.mfrac` 資産が増えてから変える費用
4. **専用の読み出し API**
   - 確かめること: ABI はスロットの末尾追加だけで増やせる (規則 11 が保証)
   - 状態は `Destructible` / `FracturePiece` の欄にあり、汎用 `GetComponentField` で読めるので、専用 API はその糖衣として足せる。ADR に 1 段落書くだけで、コードは変えない
5. **三角形分割の方式の差し替え**
   - 確かめること: libtess2 の呼び出しが `CapLoops` の中の 1 つの関数 (輪郭の列 → 三角形) に閉じていて、入出力が libtess2 の型に依存していないか
   - 依存していれば、挙動を変えずに境界の関数を切り出す (例: `TriangulatePlanarLoops`)。ADR に書く

### B. 位相的な閉じの再調査 (コードは書かない。一時的な計測プローブはよい)
今の焼きの出力で、次を数えて表にする:
- 入力: 箱 16 / L 字 12 / トーラス 32 / ボクセル化した開いた箱 16 / CesiumMan
- 数えるもの: 破片ごとの位相的な境界辺の数 (位置のビット一致の溶接の後)。その内訳 (外側面と蓋の継ぎ目 = 丸めのずれ / 蓋どうしの継ぎ目 = T 字接合 / その他)

そのうえで、実現する方式を 1 つ以上具体的に評価する。例:
- 蓋を対ごとに作るとき、Voronoi 辺の上の点を両側で共有する (Voronoi のセルの辺を先に分割点として確定し、両側の蓋のクリップに同じ点列を使う)
- 外側面のクリップ点を、元の辺と平面の組で一意に決める

各方式の規模 (行数の見積もり)、決定性への影響、下流の利点 (実行中の再分割 B の前提になる) を書く。

**結論は 3 択**:
- (i) 次のマイルストーンで実装できる
- (ii) 条件付きで可能
- (iii) 割に合わない

結論と根拠を ADR-021 の「後回し」節に書く。実装はしない (ユーザー回答どおり延期)。

### C. 文書
ADR-021 に、上の A の 5 件の「将来の拡張がどこに入るか」と、B の結論を書く。

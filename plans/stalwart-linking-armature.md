# M60: 関節と機構 (剛体トラック) — 11 サブ詳細計画

## Context

ユーザーの要求は「超リアルな物理演算を追加できるようにしたい」で、M59〜M62 の全体ロードマップは
既に `plans\greedy-cooking-wave.md` にコミット済み。M59 (剛体の基礎力学と空力) で
材料資産・環境・空力・浮力・蓄積インパルスソルバ・サブステップ・ジャイロ項・静動摩擦・
スリープ/アイランド・地形コライダーが揃い、**単体の剛体は十分にリアルになった**。

M60 が足すのは「**複数の剛体を繋ぐ層**」= 関節と機構。ロードマップの記述:

```
M60  関節と機構 (剛体トラック)
      拘束一般化 (Jacobian 行 + 蓄積λ) → ボール/ヒンジ → リミット/モータ
      → 固定/スライダ/コーン → 複合コライダー + 凸包 (クック時生成)
      → ラグドール (Parts/Skeleton 接続) → 車両 (レイキャストサス + タイヤ)
```

出口の姿は「Inspector で `Joint` を 1 つ付けるだけで、振り子・ドア・ロープ・ラグドール・
車が作れる」。**既存シーンは 1 ビットも変わらない** (M59 と同じ存在ゲート方式)。

**スコープ (ユーザー決定)**: 剛体トラックのみ。M60' (XPBD 変形体) と予約事項 1
(ステートフルバックエンド導入様式) は着手時に別計画で詰める — 本計画では扱わない。

**前提 (ユーザー決定)**: **M59 の残り 3 サブ (j / k / l) を先に消化してから M60 に着手する。**
それらの正本は `plans\greedy-cooking-wave.md` の該当節であり、本計画では再計画しない。

### M59 の申し送りのうち M60 で必ず効くもの

1. **蓄積インパルスで `1/count` 緩和を掛けてはいけない** (g1-1)。拘束行でも同じ — 律速になる。
2. **位置補正は速度ソルバから分離**しないと成立しない (g1-2)。速度反復 4 回はよいが
   **位置補正 8 回は減らせない** (g1-3)。
3. **剛性はサブステップで買える** (g2-7)。k=20000 は substeps 1 で 30.6m 伸び、4 で 0.105m。
   関節の硬さも同じ性質 — 車両が substeps 8 を要求するのは予約事項 4 のとおり。
4. **減衰はサブステップごとに掛けない** (g2-3)。関節のダンパも「毎 tick の率」で書くなら同様。
5. **`p + 0.0f` は `-0.0f` を `+0.0f` に化けさせる** (f1-4) → 値ゲート禁止・分岐ゲートで書く。
   **引き算は安全** (`x - (+0.0f) == x`)。
6. **島は静的/kinematic を繋がない / 起床は接触候補ペアの走査**  (h-6,7) →
   **関節ペアを島と起床の両方へ明示的に足さないと、繋がった片方だけが眠って関節が壊れる**。
7. **同じアーキタイプにエンティティを足すとコンポーネントポインタが死ぬ** (h-11)。試験の書き方。
8. **静的コライダーは材料なしでは e を主張しない** (g2-2)。反発を測る試験には `.physmat` が要る。

**順序の根拠**
- **可視化を a に同梱する** — M59 は可視化 (e) を面空力より前に置いて正解だった。関節は
  「アンカーがどこで軸がどっちを向いているか」が見えないとデバッグが成立しない。
- **行の一般化 → 行の追加 → 行の種類 (不等式/駆動) → 行の破断** で拘束を積み上げてから、
  形状 (e/f) と応用 (g/h) へ移る。応用サブが基盤に手戻りを起こさない順序。
- **複合コライダー (e) をラグドール (g)・車両 (h) より前に** — 胴体や車体は複数形状で作る。
- **凸包 (f) は e の後・g の前**。溢れたら f を i の後ろへ送ってよい (下記「逃げ道」)。
- **g1 (駆動) を g2 (生成器) より前に** — 生成器は「正しい形」を知らないと書けない。
  手で組んだ 3 骨のラグドールが動いてから、その形を自動で吐く器を書く。
- **h1 (サス) を h2 (タイヤ) より前に** — サスは `mg/k` という解析解を持つので、
  タイヤ力という「解析解の無い層」を積む前に土台を数字で固定できる。
- **golden は挙動が固まる最後 (k) に 1 回だけ**。

### M60a の申し送り (計画外の事実・罠)

1. ★**「1 自由度の拘束行を Gauss-Seidel で独立に解く」は成立しない。ブロックごと K⁻¹ で
   解くこと。** 計画は `ConstraintRow` (行 + 蓄積λ) を内部表現に据えていたが、行を独立に
   解くと**アンカーが質量中心から離れた瞬間に有効質量行列 K が悪条件になる**。
   半径 0.1 / 質量 1 の球を 2m 離れた点で吊った実例で K の 2x2 小行列の GS 縮小率が
   **0.967** — 8 反復しても誤差の 76% が残り、振り子のアンカーが 1 ステップで **37mm**
   ずれた (計画の受け入れ基準は 1mm)。3 自由度まとめて K⁻¹ を掛ける形 (`ConstraintBlock`)
   に作り替えたところ、同じシーンで **42µm** に落ち、周期も 176 → 170.0 tick
   (解析値 170.2) へ収束した。
   → 実装は `ConstraintBlock` (count 1..3 + 3x3 の `kinv`)。**count==1 のときだけ lo/hi の
   クランプが意味を持つ**ので、M60c のリミット (不等式 1 自由度) とモータ (駆動 1 自由度) も
   同じ箱にそのまま収まる。等式ブロックは ±実質無限大のままでクランプが結果に触れない。
   `Invert3x3` を `Solve3x3` (M59f1) の隣に追加した (余因子は同一、逆を 1 回だけ作って持つ)。
2. **リミットのフィールドは計画の「3 本」ではなく 4 本切った** — Cone が swing (円錐半頂角) と
   twist (範囲) の 2 系統を要求するため。`useLimit / limitMin / limitMax / swingLimitDeg`。
   モータは計画どおり 2 本で、**`motorMaxForce <= 0` を分岐ゲート**にして `useMotor` を持たない。
3. **`broken` の読みは a から入れてある** (行を立てない)。書くのは M60d。
   フラグ 1 本で「自由になる」が成立することを試験で固定済み。
4. **不動アンカーは「番人ボディ」で表す** — invMass 0 / invI 零行列の `Body` を 1 個持ち、
   `ai/bi == -1` のときそれを渡す。有効質量も適用も自然に「何も起きない」へ落ちるので、
   -1 の分岐をソルバの各段に撒かずに済む。
5. **アンカーの規約**: owner 側は自分のローカル、相手側は相手のローカル。
   **相手が null のときだけ `connectedAnchor` がワールド座標**という唯一の非対称。
   自動算出 (Unity の auto-configure 相当) は入れない — エディタ時ロジックが sim の契約の
   外に増えるため。
6. **位置補正は並進のみで、ボールジョイントについては厳密**。アンカーのワールド位置は
   「形状原点 + 姿勢で回した局所オフセット」なので、形状原点を誤差ぶん動かせば誤差は
   ちょうど 0 になる。だから速度行に Baumgarte を一切入れずに済んでいる。
   **角度自由度を持つ M60b 以降はこの性質が無い** (回転を直さないと軸のずれが累積する) ので、
   b は位置補正パスに**姿勢の回転**を足す必要がある。
7. **島と起床の配線は 2 箇所**: 起床走査 (接触候補ペアの直後) と `islandPairs` への追記。
   計画の警告どおりで、実測でも「土台 tick 79 / 振り子 tick 79」と揃った。
   起床は関節経由で 1 tick で伝播する (接触していない相手にも届く) ことを試験で固定。
8. 可視化は計画どおり `PhysicsDebugFlags` に 1 ビット。**ラベルは出していない** —
   `DebugLineCmd` は線しか持たず、文字を出す口が無い。代わりに
   「アンカー A=緑 / アンカー B=黄 / **2 点を結ぶ赤い線 = 拘束誤差そのもの**」の色分けにした。
   編集中 (Play 前) は tick が回らず線が積まれないので、SceneViewWindow 側にも
   SpringJoint と同じ棚でギズモを 1 つ足してある (authoring 用)。
9. 実測値: 単振り子の周期 170.0 tick (解析値 170.2) / アンカードリフト 42µm /
   2 体関節のアンカー間隔 0.147mm / 10 連鎖ロープ (substeps 4) の伸び 4.93mm (全長 5m)。

### M60b の申し送り (計画外の事実・罠)

1. ★**角度自由度には「基準の相対姿勢」が要る。M60a のスキーマにはそれが無かった。**
   a の「フィールドは c/d の分まで最初に切る」はリミット / モータ / 破断しか見ておらず、
   **b が要求する基準を見落としていた**。速度だけを拘束すると軸のずれが積分誤差として
   累積し (位置補正で戻す先が無い)、ボールジョイントで成立していた「並進だけで厳密に
   直る」性質が角度には無い。
   → `JointComponent` に `restRotation` (Quat、既定 単位) を**末尾 append** した。
   定義は `conj(qOwner) ⊗ qConnected` = 「これが rest」。相手が null ならワールドなので
   `conj(qOwner)`。既定の単位は「両者のローカル軸が揃っているのが rest」で、
   両者が無回転で置かれているふつうの authoring ではそのまま正しい。
   **1 フィールドで Hinge / Fixed / Slider / Cone の全部を賄える** — ヒンジ軸の相手側表現も
   `conj(restRotation) ⊗ axis` で導けるので、軸を 2 本持つ必要は無い。
2. **姿勢の誤差は `2·(x,y,z)`** (= 2·sin(θ/2)·軸) で取り出し、`acos` を一度も通さない。
   位置補正は反復なので過小評価は収束が遅くなるだけ。**w の符号を正へ揃える**のは
   -q と q が同じ姿勢を表すため — 揃えないと 180 度側へ回そうとして関節が裏返る。
3. **位置補正パスに「姿勢を回す」段を足した** (M60a の申し送り 6 の予告どおり)。
   並進より**先**に回す — 回すとアンカーが動くので、並進をあとに置いたほうが 1 パスで詰まる。
   回した後は `shapes::MakePose` で形状の基底を組み直す (同じパスの接触判定がこの pose を
   読むため)。質量中心オフセット付きのボディは「質量中心まわりに回して形状原点を逆算」で、
   位置積分と同じ規約に揃えてある。分配の重みは `n·I⁻¹·n` (方向ごとの回しやすさ)。
4. **縮退軸のヒンジ / スライダは Ball へ落とす** (線形だけ残す)。何も立てないと関節が
   黙って消えるので、`axis = (0,0,0)` のオーサリングミスで物体が飛ぶことはない。
5. **Inspector は type ごとにフィールドを出し分ける** (`JointFieldApplies`)。
   1 コンポーネントで 5 種類を兼ねる (決定台帳 1) 代償が「効かない行が並ぶ」ことなので、
   ここは削らない。**ソルバの type ディスパッチと対**なので、型を足したら両方に足すこと。
   `type` は生の整数ではなく名前コンボにした (並び順 = 値 0..4 で固定)。
6. **軸整列のテストだけでは四元数の経路が「たまたま単位のまま」通ってしまう**。
   最初に書いた 3 本 (ドア / 固定 / スライダ) は全部ワールド軸に揃っていて、初回から
   誤差が 0.000000 で通った。斜め軸 (0.6, 0.8, 0) と傾いた rest 姿勢 + 連続トルクの
   3 本を足して、実際に数値が動くことを確かめてある。
7. 実測値: ヒンジの軸外角速度は 120 tick で **0.000000** (軸まわりの 2.0 rad/s は不変) /
   ドアのアンカードリフト 18µm・軸ドリフト <5e-7 (900 tick) / 斜めヒンジのアンカー
   291µm・軸ドリフト <5e-7 / 固定 (傾き + 連続トルク 3.9 N·m) の姿勢誤差 3.45e-4 /

### M60c の申し送り (計画外の事実・罠)

1. ★**関節角の符号は「owner が connected に対して回った量」でなければ使い物にならない。**
   M60b の誤差回転 `qE = qB ⊗ conj(qA ⊗ qRest)` は「**B が**余分に回っている量」なので、
   そのまま角として読むと**相手が null (ワールド) のとき `qE = conj(qOwner)`** になり、
   ドアを +30° 開くと関節角が -30° になる。ツイスト取り出しでベクトル部だけ符号反転して
   owner 基準へ倒した。モータ目標速度・リミット下限上限・スライダ変位まで全部この規約に
   揃えてある (`+` なら owner が +軸まわり / +軸方向)。
2. ★**`JointRelativeQuat` では w を含む 4 成分すべてを反転する。** M60b は
   「w<0 なら xyz だけ反転」で足りていた (回転ベクトルしか使わないため) が、M60c は
   `(ベクトル部·軸, w)` を**半角 sin/cos の 1 組**として読むので、w を負のまま残すと
   組が食い違って角度の符号が壊れる。M60b の関数を割って共通化した (出力ビットは不変)。
3. **`acos` も `atan2` も 1 回も通していない** (計画の「cos しきい値」を一歩進めた形)。
   θ の大小比較は **θ/2 の大小比較と同値** (w を正へ揃えると θ/2 ∈ [-90°,90°] で単調)
   なので、しきい値を tick 頭に 1 回だけ半角 sin/cos へ落とせば、比較は
   `sin(θ/2 − 上限/2) = s·cosHi − c·sinHi > 0` の**掛け算と引き算だけ**で書ける。
   位置補正で戻す量も `2·sin(はみ出し/2)` = **常に過小評価**なので行き過ぎない。
4. ★**リミットは位置補正にも足さないと成立しない。** 速度行だけだと範囲外で静止した関節は
   `cdot == 0` で λ が立たず**永久に戻らない**。計画の受け入れ条件「越えた状態から範囲内へ
   復帰する」がそのまま「位置補正が要る」の証明になっている (試験 c-2)。
5. **行き過ぎは「行が立つ前に 1 サブステップ進むぶん」= 速度×h**。分岐ゲート (範囲外に
   出たときだけ行を立てる) の構造上ゼロにはできない。実測でヒンジ substeps 1 = -31.85°
   (リミット -30°) が substeps 4 で -30.00° へ。**剛性はサブステップで買える** (M59g2-7) が
   リミットにもそのまま効く、が数字で出た。
6. **モータとリミットを両方付けたらリミットが勝つ** — Gauss-Seidel は後の行が最後の一声を
   持つので、**モータ → リミットの順に積む**。逆順だとモータの目標速度が残って可動域を
   突き抜ける。スライダのモータがリミットへ貼り付く試験 (c-5) がこれを固定している。
7. **`maxForce` の上限は `maxForce·h`** (h = サブステップの刻み)。λ は力ではなく**力積**
   なので、刻みを掛けてはじめて「最大 N (角なら N·m)」になる。実測で τ/I·t の解析値と一致。
8. **試験は「たまたま境界に着地する」ことがある** — スライダを x=0 から 2 m/s で走らせると
   30 tick でちょうど 1.0 に着き、**行き過ぎ経路が一度も走らないまま緑になった**。
   開始位置を 0.05 ずらして初めて 1.0167 が出た。M60b-6 の「軸整列だけだと四元数の経路が
   通ってしまう」と同じ種類の罠。
9. **可視化は足していない**。M60a のアンカー表示のままで、可動域の円弧やコーンは描かない。
   ラグドール (g) で「どこまで曲がるか」が見えないと辛くなるはずなので、そのとき足す。
10. **既知の限界**: 四元数から角を取る以上 θ は [-180°,180°] に折り返る = **回転数を
    数えない**。無限に回るモータとリミットの併用は想定外 (跨ぐには 140 rad/s 級が要る)。
11. 実測値: ヒンジのリミット substeps 1 = -31.846°/静定 -30.000° (substeps 4 で -30.000°) /
    範囲外 -45° からの復帰 -10.000° / 無負荷モータ 3.000000 rad/s / モータ頭打ち
    5.00000 rad/s (解析値 5.00000) / スライダのリミット行き過ぎ 16.7mm・静定 1.00000 /
    コーン swing 20.839° (リミット 20°) / twist 45.827° (リミット 45°)。

### M60d の申し送り (計画外の事実・罠)

1. ★**粘着の単位は「面積 × 応力」ではなく N (力) にした。** 計画は
   `-adhesion·area·dt` だったが、**ソルバは接触面積を持っていない** — マニフォールドは
   最大 4 点で、面積を出す情報がどこにも無い (出すなら凸包 (f) の面クリップが要る)。
   `adhesion` = 「このペアが支えられる引っ張り力 [N]」に倒し、下限を `-adhesion·h` に
   した。λ が力積なのでモータの `maxForce·h` (M60c-7) と同じ換算。
2. **粘着の下限を開けるのは中央法線インパルスだけ**。点ごとの行 (M59g1 の 2 段目) は
   回転の不均衡を配るだけなので 0 のまま — 点ごとに負を許すと、吊った物体が
   マニフォールドの点の取り方しだいで勝手に回り出す。副作用として、**粘着だけで
   ぶら下がっている間は摩擦が効かない** (摩擦の枠が `totalJn > 0` ゲートの内側) が、
   ラグドールにも車両にも関係しないので v1 では許容する。
3. ★**破断に数えるのは反力だけ。モータ行は数えない。** 等式行とリミット行は
   「関節が受け止めている力」だが、モータは駆動なので、数えると**モータを強くしただけで
   自分の関節が折れる**。`ConstraintBlock::breakJoint` を -1 にして集計から外してある。
4. **判定量は「tick 全体の力積 ÷ dt」= 平均反力**。サブステップの h で割ると
   substeps を変えた瞬間に閾値の意味が変わる。集計も tick 全体で溜める。
   **足すのは力積ベクトル** — ブロックごとに |λ| を足すと、押しと引きが打ち消し合う
   場面で反力を過大評価する (ブロックの d は正規直交なので Σλ·d がそのまま力積)。
5. **λ を読むのは反復ループの外で 1 回だけ**。中で読むと収束前の途中経過まで足してしまう。
6. **判定は tick の末尾**。折れた関節はその tick ぶんは働き、行が消えるのは次 tick から
   (途中で消すと同じ tick 内で解いた λ と辻褄が合わなくなる)。
7. `JointLink::jc` を**非 const へ変えた** — `broken` を書く先が要るため。書くのは
   tick 末の 1 箇所だけで、コンポーネントの付け外しはしない (決定台帳 5)。
8. **`broken` が hash 対象であることが、snapshot 往復と .rep 追従の全根拠**。
   フィールドがハッシュに載っていれば SimSnapshot も ReplayFile も自動で従うので、
   専用の保存経路は 1 行も要らない (試験 d-4 がこれを固定)。
9. **Ball には breakTorque が働く余地が無い** (角ブロックを 1 つも立てない) ので
   Inspector で出し分けた。`JointFieldApplies` の `usesAngular` をそのまま流用。
10. **既存の `.physmat.json` 4 種は触っていない** — `adhesion` 未記載 = 0 で、
    前方互換読み (contains + 既定値) がそのまま効く。エディタから保存し直したときだけ
    `"adhesion": 0.0` が書き込まれる。
11. **計画外の発見**: `PhysicsSystem.cpp` の「転がり抵抗の軸と有効慣性 (M59f2)」ブロックが
    **31 行まるごと重複していた** (HEAD 時点で既存)。2 回目は 1 回目と同じ入力から同じ値を
    書くだけの冪等な死にコードなので挙動には出ない。M60d の範囲外なので**触っていない** —
    別コミットで消すこと。
12. 実測値: 破断力 9.9 で保持 / 9.7 で破断 (解析値 mg = 9.81 N) / 破断トルク 9.9 で保持 /
    9.7 で破断 (解析値 mg·d = 9.81 N·m) / モータ 30 N·m は breakTorque 5 でも折らない /
    粘着 30N は 1kg (9.81 N) を y 0.3005 で保持し 5kg (49 N) は落とす。

### M60e の申し送り (計画外の事実・罠)

1. ★**`Body::col` は動的ボディにしか入っていない。** 静的コライダーは `pose` だけ作って
   `col` を持たない (収集コードを読めば分かるが、名前からは絶対に想像がつかない)。
   「自分自身の形状を持つか」を `col` の有無で代用したら**世界中の床が消えた** —
   接触がゼロになり、全部が落ち続けて selftest が 18 秒から 10 分超へ化けた。
   専用フラグ `ownShape` を切って直した。**次に「形状を持つか」を判定するときも同じ罠**。
2. **ブロードフェーズは計画の「子形状ごとのエントリ」ではなく「和の AABB 1 個」にした。**
   ペアキーが body ベースのままなら `SolidContact` の意味も統合処理も一切いじらずに済む。
   候補列は真の接触集合のスーパーセットであればよい (`Broadphase.h` の契約) ので、
   和の AABB でも正しい。緩いぶん偽候補は増えるが、子形状が数個の v1 では問題にならない。
3. **狭域は形状ペアごとに `ContactConstraint` を 1 本ずつ作る** — 法線が形状ごとに違うので
   1 つのマニフォールドには畳めない。出力側で**隣り合う同一キーを 1 件へ統合**する
   (生成順が候補ペア昇順 → 形状ペアの入れ子なので同じキーは必ず隣接する)。
   インパルスは足し、幾何は**最も強く押した子形状**を代表にする。
4. ★**慣性は 3x3 フルテンソルが要る。** 平行軸で合成すると必ず非対角が出る (L 字が典型)
   ので、対角しか持てない `InvInertiaWorld` では表現できない。局所で 1 回だけ
   `Invert3x3` (M60a) して `invILocal` を持ち、毎サブステップ `B·I⁻¹·Bᵀ` で世界へ回す。
   → 副作用として**ジャイロ項 (M59f1) は複合では効かない** (主軸ローカルで解く実装なので
   フルテンソルを渡せない)。対角だけで近似すると黙って間違うので、効かせないほうを選んだ。
5. **v1 の制限を 3 つ明記した**: ①密度からの質量導出は親自身の形状しか見ない
   (複合の質量は `mass` で与える) ②材料・レイヤーは body 単位で、親の Collider が
   無ければ最初の子から採る ③CCD は親自身の形状しか掃かない (親が形状を持たない複合は
   外接球半径 0 で起動しきい値から自然に外れる)。
6. **子形状の順序は (親 index, 子 index) 昇順で明示的に固定する。** 慣性の足し算は fp
   なので順序が結果のビットを決める — アーキタイプの走査順に依存させてはいけない。
7. **合成は `bodies` の並べ替えのあと** (subFirst/subCount は並べ替え後の添字)。
8. **2 段階ビルドの証明が計画どおり効いた**: ①フィールドだけ追加 → `[phys]` 91 行のうち
   **ハッシュ 10 行だけが動き、実測値 81 行は完全一致** ②配線後 → **91 行すべて①と一致**。
   「ハッシュのバイト列は変わるが挙動は不変」がこの 2 段で機械的に示せる。
9. 実測値: 複合の慣性 ω_z = **1.20000** (等価な単一 box も 1.20000、解析値 1.20000) /
   体積加重の重心で吊ると重い側が真下 (y = -1.0000) / 明示 `centerOfMass` はそれに勝つ /
   子形状 2 個で着地しても**接触の報告は 1 件**。

### M60a: 拘束ソルバ基盤 + ボールジョイント + 可視化

拘束の**内部表現**を入れる、本マイルストーンで最重量のサブ。

- **`ConstraintRow`** (PhysicsSystem.cpp の無名 namespace、`SolidContact` とは別物):
  `bodyA / bodyB` (index、-1 = 不動)、腕 `rA / rB`、方向 `n` (線形行) または軸 `a` (角行)、
  生成時に確定する `effMass` と `bias`、クランプ `lo / hi`、蓄積 `lambda`。
  行の適用は既存 `ApplyImpulse` / `MulInvI` / `Cross` を再利用する (新規の数学は書かない)。
- **`JointComponent` (TypeId 40)** — 末尾 append。フィールドは c/d の分まで最初に定義する
  (a1 でスキーマを先に切った M59 と同じ流儀。後から足すと版が動く):
  `connectedEntity` (null = ワールドへの不動アンカー) / `type` (0=Ball 1=Hinge 2=Fixed
  3=Slider 4=Cone) / `anchor` / `connectedAnchor` / `axis` / リミット 3 本 / モータ 2 本 /
  破断 2 本 / `broken` (sim 状態 = hash 対象)。
  **`type` は「どの行を立てるか」のプリセット**であって別実装ではない:
  Ball = 線形 3、Hinge = 線形 3 + 角 2、Fixed = 線形 3 + 角 3、Slider = 線形 2 + 角 3、
  Cone = 線形 3 + 不等式 2。**a では Ball のみ通す** (残りは b/c で行を足すだけ)。
- **差し込み位置**: 生成は :1428 の接触制約生成の直前、解決は :1669 の反復ループの
  **各反復の先頭** (関節 → 接触の順)、位置補正は :1828 のパス内で接触より先。
  サブステップごとに行を作り直す (姿勢が変わるため)。λ の蓄積はサブステップ内で閉じる。
- **決定論の順序**: 行の生成順 = owner の entity.index 昇順 → 同一 owner 内は行番号昇順。
  相手 body の解決は SpringJoint と同じ二分探索 (:952 の流儀)。
- **島と起床への配線 (M59h の穴)**: 関節ペアを `islandPairs` へ足す。起床走査 (:1389) にも
  関節ペアを含める。**これを忘れると振り子の片方だけが眠って関節が破綻する**。
- **SpringJoint は 1 行も触らない** — 既存シーンのビット同一を守る。新基盤で距離拘束は
  表現できるが、移行はしない (engine_spec に「SpringJoint は互換維持の旧式」と明記)。
- **可視化 (`PhysicsDebugFlags` に 1 ビット追加)**: アンカー 2 点 (ずれが見える) + 軸 +
  ラベル。M59e の `BuildPhysicsDebugLines` を拡張。
- 触点: Components.h / Components.cpp (末尾 append + `MYE_JP` 表示名) / LocalizationTable.inl /
  Create メニュー (「ジョイント」) / Inspector (connectedEntity の EntityRef、type コンボ) /
  PhysicsDebugDraw / gen_project_files.ps1 (新規ファイルを作る場合)。
- **検証**: (i) 存在ゲート — Joint 無しのシーンが 2 段階ビルドで `[phys]` ログ全行一致
  (a2/f1 と同じ手順)、(ii) 単振り子の周期が解析値 `2π√(L/g)` の窓に入る、
  (iii) アンカー距離誤差が N tick 後も 1mm 未満 (ドリフトしない = 位置補正が効いている)、
  (iv) 2 体を繋いだ系の運動量保存、(v) 10 連鎖のロープが伸びない、
  (vi) 並走ハッシュ、(vii) 関節で繋がった 2 体が**同じ tick に揃って眠る** (M60a の島配線)。

### M60b: ヒンジ / 固定 / スライダ

- **角拘束行**の一般化 (a では線形行しか無い)。ヒンジ = 軸直交の 2 方向を角度で拘束、
  固定 = 相対姿勢 3 自由度、スライダ = 軸直交の線形 2 + 角 3。
- 相対姿勢の誤差はクォータニオンから取る。**`XMVECTOR` 禁止 (決定論契約)** —
  PhysicsSystem.cpp :58-88 の scalar `QuatMul` / `QuatRotate` を使う。
- Inspector: `type` に応じて意味のあるフィールドだけ出す (M59 の Aero の bool ゲートと同じ発想)。
- **検証**: ヒンジ軸まわり以外の角速度が N tick 後に消える / ドアが軸から外れない /
  固定ジョイントの相対姿勢がビット窓で保存 / スライダが軸上のみ動く / 並走ハッシュ。

### M60c: リミット + モータ + コーン

- **片側不等式行** (λ を `[0, ∞)` にクランプ) が新しい行の種類。リミットは
  「範囲外に出たときだけ行を立てる」= 分岐ゲート (値ゲートにしない)。
- **モータ** = 目標速度を bias に持つ両側行で `|λ| ≤ maxForce·dt` にクランプ。
  角度モータ (ヒンジ) と線形モータ (スライダ)。
- **コーン (swing/twist)** = ボール + swing 角の不等式 1 行 + twist 角の不等式 1 行。
  ラグドール (g) が唯一の実需要なので、g で必要な形に合わせて切る。
- **三角関数の扱い**: リミット角は**フィールドは度で持ち、比較は cos の閾値**にして
  `acos` を毎 tick 通さない (決定論上も速度上も有利)。閾値は生成時に 1 回だけ計算。
- **検証**: リミット角で停止して越えない (窓) / 越えた状態から範囲内へ復帰する /
  モータが定常速度へ収束し `maxForce` で頭打ちになる / モータ off とリミット off が
  それぞれ「行を立てない」= b とビット同一 / 並走ハッシュ。

### M60d: 破断 + 粘着性

- **破断**: その tick の λ 合計が `breakForce`/`breakTorque` を超えたら `broken = true`。
  以後その関節は行を立てない。**`broken` は sim 状態 = hash 対象**で、コンポーネントを
  外すのではなくフラグで落とす (構造変更をソルバ内から起こさない = M59 の家風)。
  復帰は Inspector / スクリプトが `broken` を false に戻すだけ。
- **粘着性 (adhesion)**: ロードマップの表で M60 に割り当てられている「法線インパルス下限を
  負まで許可」。`.physmat.json` に `adhesion` キーを足し (a1 で「後から足せる」と明文化済み)、
  接触の法線λクランプ下限を `-adhesion·area·dt` 相当まで開ける。
  **結合則は min** (弱いほうが勝つ = 摩擦/反発と揃う) で明文化。
  材料未割当なら下限は 0 = **従来とビット同一**。
- **検証**: 閾値直下で壊れず直上で壊れる / 壊れた瞬間から自由落下 / `broken` が
  snapshot 往復と DLL リロードを跨いで保つ / 粘着 0 のシーンがビット同一 /
  粘着材料で天井にぶら下がる → 質量を増やすと落ちる。

### M60e: 複合コライダー

- **規約**: `Rigidbody` 末尾 append の `bool compoundColliders = false` で **親側が opt-in**。
  true のとき、Rigidbody を持たない子孫の `Collider` を**その剛体の形状として集約**する
  (現状は「静的コライダー」として別枠で収集されている = 挙動が変わるので既定 off は必須)。
  AeroSurface (M59d) の「最も近い Rigidbody 祖先へ集約」と同じ探索を使う。
- **慣性**: 子形状ごとに `LocalInertiaDiag` (:189) を出し、**平行軸で合成**する。
  ★M59f1-5 の「形状から導いた対角慣性を移し替えない」は**単一形状の話** —
  複合では移し替えが正当 (質量分布が実際に分かっているため)。ここは意図的な非対称なので
  コメントで理由を残す。質量中心も形状体積の加重平均で導く (`Rigidbody.centerOfMass` は
  明示指定があればそちらが勝つ = 既存規約を壊さない)。
- **衝突**: 複合ボディは子形状ごとにブロードフェーズ AABB を出し、マニフォールドも
  子形状ごとに作って**同じペアキーへ統合**する (SolidContact の意味を変えない)。
- **検証**: L 字の複合体が「重い側を下にして」静定する (単一 box では起きない) /
  複合の慣性が解析値の窓に入る / off のシーンがビット同一 / 並走ハッシュ /
  接触出力のペアキーが子形状ごとに増えていないこと。

### M60f: 凸包クック + 凸形状の衝突

- **`shape = 5` (convex)**。データは `.mmdl` / `.mpcm` の隣に**第 3 のクック種**として置く
  (`CookedCache` + `ModelCook` の流儀。`meshcol::` と同じ注入で解決)。
- **凸包生成は決定論的 QuickHull** — 入力頂点の重複除去と処理順を「(座標, 元 index) の
  明示ソート」で固定する (BVH 構築が `centroid + 三角形番号` のソートで決定論を作ったのと同じ手)。
  結果は面 (平面) + 頂点 + 稜線の 3 表。
- **衝突は SAT** (面法線 + 稜線×稜線) → 参照面クリップで最大 4 点マニフォールド。
  凸 × 球 / 箱 / カプセル も同じ経路へ寄せる。**凸 × メッシュ (shape=3) は対象外**
  (静的メッシュ側の三角形を「凸」として扱えば通るが、v1 では約束しない)。
- **★逃げ道**: このサブが溢れたら「凸包の生成とクックまで (= 静的コライダーとしての利用)」で
  1 コミット切り、凸×凸のマニフォールドを i の後ろへ独立サブとして送る。
- **検証**: 生成が入力頂点順に依らずビット同一 (順序をシャッフルした入力で照合) /
  箱の頂点群から作った凸包が箱の解析衝突と一致する窓 / 凸多面体が斜面で安定に静止 /
  クック往復 (`.sealed` 封印も) / 並走ハッシュ。

### M60f の申し送り (計画外の事実・罠)

1. ★**稜線×稜線の分離量は「投影区間」で測らないと三角形で破綻する。** 定番の
   `dot(axis, p2 - p1)` は**軸が Minkowski 差の面法線であること**が前提の式。三角形は
   「表裏 2 面の潰れた凸体」なので隣接 2 面の法線が逆向き = `cross(n1, n0)` が零ベクトルになり、
   Gauss map の枝刈りが判定不能になる。枝刈りを外す (= 安全側) と無効な軸が専用式へ流れ、
   **接触した瞬間に「分離している」と誤答して凸包が静的メッシュ床をすり抜けた**。
   両者の投影区間 (min/max) で測れば軸の向きにも枝刈りの有無にも依存しない。
   面軸は本物の面法線なので専用式のままでよい (非対称だが理由がある)。
2. **生成は QuickHull ではなく総当たりの逐次追加にした。** QuickHull の面隣接構造は
   「地平線が非多様体になった」ときの復旧が難しく、縮退入力で静かに壊れた凸包を返す。
   逐次追加なら可視面と地平線を毎回その場で数え直すので、破綻したらその点を捨てて先へ進める。
   頂点上限 (kConvexMaxVerts=64) のおかげで実測コストも問題にならない。
3. ★**同一平面の三角形を多角形面へ統合するのは必須。** 統合しないと箱の凸包が 12 枚の
   三角形のままになり、参照面クリップの接触点が 3 点で頭打ち = box-box の 4 点マニフォールドと
   同じ安定性が出ない。統合後は箱の凸包が 8 頂点 / 6 面 / 12 稜線 (オイラー) にきちんと一致する。
4. **クックの key 問題は AssetID の逆引きで解けた。** `MeshLibrary::names_` に
   `"<正規化絶対パス>#mesh0#prim0"` が残っているので `#` の手前がクック元パスになる
   (`MeshLibrary::NameOf` を新設)。手続き生成メッシュは `#` を持たないか実ファイルが無く、
   CookedCache 側が stat に失敗して自然に無効化される = **特別扱いのコードが要らない**。
   `.mcvx` は「モデル 1 ファイル = 表 1 個」で、要求されたメッシュの分だけ遅延で書き足す
   (ロード時に全メッシュ分焼かないのは、どれを凸包にするかを知っているのがモデルではなく
   シーン = `Collider.shape=5` だから)。**封印キャッシュ (`.sealed`) には書き足さない**。
5. **CookedCache に第 3 の種を足す手数はゼロだった** (計画の「f 冒頭で潰す」項目の答え)。
   magic / version / 封印の検証はヘッダ共通で、`ReadValidated` / `Write` に拡張子を渡すだけ。
   退避案 (ランタイム生成 + メモリキャッシュ) は不要だった。
6. ★**Collider にフィールドを 1 つも足していない** — `meshAsset` を shape=3/4 と共有する
   第 3 のタグ付き共用体にしたため。結果として**既存シーンはワールドハッシュのバイト列すら
   変わらない**。M60e が 2 段階ビルドで示した「バイト列は変わるが挙動は不変」より強い形で、
   存在ゲートとしては理想形になった。
7. **慣性のフル 3x3 は `subCount > 0` では判別できない。** 複合 (M60e) と凸包 (M60f) の
   2 通りが要るので `Body::fullInertia` を切った。凸包の質量特性は四面体積分
   (共分散 `C = ∫x xᵀ dV` を貯めて `I = tr(C)E − C`)。**非一様スケールでは慣性が相似変換に
   ならない**ので、毎回スケール後の頂点で積分し直す (頂点 64 なら収集時 1 回で十分安い)。
   副作用は M60e と同じ — **ジャイロ項 (M59f1) は凸包でも効かない**。
8. **球とカプセルは SAT に載せない。** 丸い形は「頂点と球心を結ぶ軸」が分離軸になり得て、
   面法線と稜線外積の列挙では取りこぼす。凸包への符号付き距離 + 表面最近点で解き、
   カプセルは芯に沿った**固定 32 回の黄金分割** (capsule-box が既に採っている手) にした。
9. **`-0.0` は入力で `+0.0` へ畳む** (値ゲートではなく分岐ゲート)。畳まないと
   「入力に -0.0 と +0.0 が混ざっているとき重複除去でどちらが残るかが入力順で変わる」=
   生成が入力順に依らないという主張が崩れる。
10. **Inspector のコライダー形状コンボは 3 件しか出していなかった** (Mesh / Terrain は
    "(invalid)" 表示で、シーン JSON を手で書く以外に選べなかった)。M60f で 6 件へ広げた —
    **エディタ表示のみの変更**で sim は 1 ビットも動かない。
11. 実測: 凸包の立方体が箱コライダーと**同じ高さで静止** (どちらも y = 0.49950) /
    慣性 ω_z = **1.20000** (等価な box も解析値も 1.20000) / 凸×凸・凸×球・凸×カプセル・
    凸×三角形スープすべて着地 / 接触の報告は 1 ペア 1 件 / 400 点の球点群を並べ替えても
    凸包が**バイト同一** / `[phys]` 103 行が Debug と Release で完全一致。

3. ★**休止中の骨は作業コピーだけでなく `rb->velocity` 自体を 0 に落とす必要がある。**

5. **切替の連続性は「設計の配当」で、初期化コードは 1 行も書いていない。** false→true の

6. **セルフテストのスケルトンは手で組んだ** (`RagdollSelfTest.cpp` 内の 3 骨直鎖 + 1 クリップ)。

7. **描画の分岐は `RenderSystem::Render()` の中 = ビュー毎に走る**。パレットが ECS 状態の

8. **v1 の制限**: ①ラグドール部位は M48g の v1 規約どおり SkinnedMesh の**直子**でなければ

   刺さっていたら**先勝ち** (兄弟順はワールドハッシュに載っていないので、後勝ちにすると
   「ハッシュは同じなのに絵が違う」が起きうる) ③物理とアニメのブレンドは約束しない。
9. 実測値: 休止中 120 tick で部位の位置が**アニメの値とビット一致** / 剛体を消した

### M60g1: ラグドール駆動 (剛体 → 骨)

**TypeId 41 = Ragdoll。生成器は g2、ここは「手で組んだラグドールが動く」ところまで。**

#### 骨 ↔ 剛体の結び方 — `PartComponent` を再利用する (決定台帳 12)

ラグドール部位 = **`Part`(joint 名) + `Collider`(カプセル) + `Rigidbody` + `Joint`(Cone)** を
持つ、SkinnedMesh の**直子**エンティティ。新規 TypeId は `Ragdoll` の 1 個だけ。

- 骨名解決 (`SkinnedModel::FindJointByName`)・source 解決 (`Parts::ResolvePartSource`)・
  Inspector のジョイントコンボ (`InspectorWindow.cpp:1156-1216`) が**全部そのまま使える**。
- ★**逆行列を 1 つも書かずに済む**のが最大の利点。`PartFollowSystem` の v1 規約
  (部位は source の直子 = `partLocal == jointGlobal`、`PartFollowSystem.h:22-28`) を
  そのまま逆に読めばよい。`XMMatrixDecompose` を避けている理由 (構成間でビットが割れる) にも
  触らずに済む。
- 代償は「骨の親子関係をエンティティ階層で表せない」こと。だが**親子は `Joint` が作る**ので
  物理的には不足しない。むしろ平坦なほうが `LocalTransform == jointGlobal` が保てる。

#### `RagdollComponent` (TypeId 41) — SkinnedMesh 側に付く札

- `bool active` (**hash 対象** = sim 状態)。アニメ駆動 ⇔ 物理駆動の切替。
- v1 ではこれ 1 本。**予備フィールドは切らない** — M60a の「c/d の分まで先に切る」は
  M60b が基準姿勢を見落として結局 append した前科があるので、
  **見えていないものは切らない**方針へ倒す。
- `Components.cpp:685` の `});` の直後 = `RegisterBuiltinComponents()` の末尾へ append。

#### 3 つの経路を足す

1. **物理側 (収集)**: `active == false` のラグドール部位は **kinematic として扱う**。
   ★`RigidbodyComponent.isKinematic` を**書き換えない** — Inspector の値を潰すし、
   ソルバがコンポーネントを書くのは家風でない。収集時 (`PhysicsSystem.cpp:1016-1105`) に
   「Part → source → Ragdoll.active」の 2 段引きで分岐する。
   ★**分岐ゲートで書く** (M59f1-5 / M60e-1) — 「係数 0 を掛ける」形にすると `-0.0f` 化けで
   ワールドハッシュが動く。Ragdoll 非所持シーンは**ルックアップのみで fp 演算ゼロ**。
2. **Part 側 (抑止)**: `PartFollowSystem::Update` (`PartFollowSystem.cpp:188-194`) で、
   source に active な Ragdoll があれば**その部位を skip** する。
   skip しないと同 tick で「骨 → 部位」(`:192`) と「物理 → 部位」(`:3917-3955`) が
   両方 `LocalTransform` (hash 対象) を書き、部位が二重駆動される。
3. **描画側 (パレットの第 2 経路)**: `RenderSystem.cpp:744-765` に分岐を足す。
   source に active な Ragdoll があれば:
   - 子を走査して `Part.joint` → jointIndex の対応を作り、`global[j] = 部位の LocalTransform`
     (行ベクトル TRS を組む。`PartFollowSystem.cpp:36-87` の `DecomposeRowMajorTRS` の逆)
   - **部位を持たない骨**は `global[j] = local[j] * global[parent[j]]` で埋める
     (`local` はアニメの `ComputeJointLocals`)。★親が自分より先に確定している必要がある —
     **joints 配列が親→子順に並んでいることを最初に検査**し、並んでいなければ
     `JointGlobalFromLocals` (`Skeleton.cpp:113`) と同じ「親チェーンを上へ」の形へ落とす
   - `palette[j] = transpose(inverseBind[j] * global[j])`
   → **入力は ECS 状態 (Part の LocalTransform) だけ = 純関数**なので、ビュー毎に組み直しても
     同じ絵になる。`skinPalettes_` のフレーム毎クリア (`RenderSystem.cpp:570`) とも整合。

#### `active` 切替の連続性

`active` を false→true にした瞬間、部位の `LocalTransform` は**アニメが置いた骨姿勢そのもの**
なので剛体の初期姿勢が飛ばない (これが Part 再利用のもう 1 つの利点)。速度は 0 から始まる。

約束しない** (計画どおり)。`SkinningSystem` は `sm->playing = 0` で止められる (非ハッシュ)。

## 決定台帳 (M60 の設計判断)

| # | 論点 | 決定 |
|---|---|---|
| 1 | 関節の粒度 | **単一 `JointComponent` + `type` プリセット**。型ごとの別コンポーネントにしない — 内部表現は「行の集合」で共通なので、別型は Inspector 上の見た目の差でしかない。将来の完全 D6 (軸ごとに free/limited/locked) も同じ箱に入る |
| 2 | 1 エンティティ 1 関節 | ECS のアーキタイプ SoA に従い**この制約を受け入れる**。関節は必ず「子側」に置く規約 (ラグドールの骨も車輪も自然に片側 1 個)。複数要るケースは中間エンティティを挟む |
| 3 | 解く順序 | **関節 → 接触** を各反復の中で固定。貫通のほうが目に見えるので接触を最後に解く。位置補正パスでも同順 |
| 4 | SpringJoint の扱い | **移行しない**。既存シーンのビット同一が最優先。engine_spec に「互換維持の旧式」と明記 |
| 5 | 破断の表現 | `broken` フラグ (hash 対象)。ソルバ内からコンポーネントを外さない (構造変更はコマンドバッファ tick 末が家風) |
| 6 | 複合コライダーの opt-in | **`Rigidbody.compoundColliders` (bool、既定 false)**。子側にマーカーを置く案より TypeId を消費せず、ゲートが 1 箇所に閉じる |
| 7 | 複合の慣性 | 平行軸で合成する (単一形状では移し替えない M59f1-5 との**意図的な非対称**。複合では質量分布が実際に分かっている) |
| 8 | ラグドールの骨駆動 | **描画側でボーンパレットを組む**。ハッシュ対象は剛体の LocalTransform のまま = 決定論の面積を広げない |
| 9 | 車両の実装 | 拘束ではなく**レイキャストサス + 力**。~~既存 `RaycastWorld` を使う~~ → **13 で撤回**。入力はフィールド = ABI 追加ゼロ |
| 10 | 挙動バージョニング | しない (M59 決定台帳 8 の継続)。ただし M60 は**全機能が存在ゲートの内側**なので、既存シーンのビットは a〜k を通して 1 つも動かない見込み |
| 11 | リミットの三角関数 | 生成時に cos 閾値へ 1 回だけ変換。毎 tick の `acos` を通さない |
| 12 | ラグドールの骨結合 | **`PartComponent` を再利用する** (ユーザー決定)。ラグドール部位 = Part(joint 名) + Collider + Rigidbody + Joint。骨名解決・source 解決・Inspector コンボが既存のまま使え、`partLocal == jointGlobal` の v1 規約を逆に読むだけなので**逆行列を 1 つも書かない**。新規 TypeId は Ragdoll(41) の 1 個 |

## 検証の柱

1. **存在ゲートのビット同一** (全サブ): 2 段階ビルド (フィールドのみ ⇔ 配線後) で
   `[phys]` ログ全行照合。**ハッシュ値そのものを前コミットと比べても意味が無い**
   (フィールド追加で必ず動く) — M59f1-9 の手順が正本。
2. **解析解との一致** (a, c, e, h1): 単振り子の周期 / モータの定常速度 / 複合の慣性 /
   サスの沈み込み `mg/k`。
2'. **パレットが ECS 状態の純関数** (g1): 同じ world から 2 回組んで `memcmp` 一致。
   `RenderSystem::Render()` はビュー毎に呼ばれるので、これが崩れると
   **SceneView と GameView で絵が割れる** (決定論ではなく描画の一貫性の柱)。
3. **拘束誤差のドリフトゼロ** (a〜d): アンカー距離誤差が長時間 tick で増えないこと。
   これが「位置補正が効いている」唯一の機械的証明。
4. **島と起床の配線** (a): 関節で繋がった系が**揃って眠り、片方を叩けば揃って起きる**。
5. **並走ハッシュ決定論** (全サブ): 同一シーン 2 個並走の per-tick ハッシュ一致。
6. **replay_verify 6 ペア目** (i 以降): Debug ⇔ Release。
7. **golden は最後に 1 回** (k)。
